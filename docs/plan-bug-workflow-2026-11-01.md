# 方案：bug 工作流整合（bot 的运行底座 + bugpoll 的修复流程）

> 立于 2026-11-01（aven），**已拍板（D1–D3 见三），B1–B4 已于 11-01 全部合入并上线**（B5 按 D1 不做）。按「五、分批」逐批做，每批另开 worktree（`lark/bugflow-<n>`），合完即删。
> 一句话：bug 的发现改成「读新 bug 通知 + 低频对账」，一条 bug 一个 bot 任务，按项目号拿上下文 / worktree / 群，按仓库配置决定分支怎么开、能改谁的代码、表怎么回写。

## 一、为什么做

两套现成的东西各好一半：

| | lark-bot 的 bug 轮询器（fameex） | bugpoll（`~/.lark-bugpoll`，falive） |
|---|---|---|
| 好在哪 | 运行底座：一条 bug 一个任务（领取租约、重试、死信、回写重试、告警、doctor、自修、回放与变异闸）；按项目号分 worktree / PRD / 群 | 修复流程：一单一分支从基线切、单独推 MR；Bug 号 + 文件两层查重；手动修的占用标记；端口分段；收尾核对已推送；修复质量门槛；读评论、验退处理、分类分配 |
| 差在哪 | 只领「负责人 = 我」；2 分钟整表轮询、手动开关、空闲 4 小时自动关；只本地提交；群按群名找 | 一轮一个大 Claude，失败只能等下一轮；没有任务状态 / 重试 / 告警；falive 的值写死在 6 个脚本里；单项目，没有项目号概念 |

目标：用 lark-bot 的底座跑 bugpoll 的流程，按仓库配置，fameex 先用。

## 二、已定的口径（aven 11-01）

1. **发现 bug 靠读通知，不靠整表轮询。** 新 bug 分到我头上时，表格自动化「EX项目bug统计表」会私聊发卡片（需求 ID + 问题标题）。bot 用**我的身份**读这个私聊会话（会话 id `oc_126f01b1ed05c705c9332b49e6b234eb`，11-01 实测 `+chat-messages-list --as user` 可读；卡片里没有记录 id，要按「需求ID + 标题 + 负责RD = 我」查一次表定位记录）。
2. **两个都是轮询，分「平时 / 测试中」两档，频率按配置：**

   | 状态 | 读通知 | 对账（捞验退、漏掉的通知、状态变化） | 切换 |
   |---|---|---|---|
   | 平时 | 每 60 分钟 | 每 120 分钟 | 读到新 bug 通知 → 自动转「测试中」，私信一句 |
   | 测试中 | 工作时间 09:50–19:10 每 1 分钟，其他时间每 10 分钟 | 每 15 分钟 | 连续一个工作日（只算工作日 09:50–19:10）没有新通知 → 自动回「平时」，私信一句 |

   手动切：私信「开始测试 / 结束测试」或 `lark-bot poll-on / poll-off`。
3. **开关是全局的一个，不按项目号**（aven 11-01：现实中多项目并行，不会按项目号开）。多项目天然支持：每条通知自带需求 ID，按项目号分流、项目间并行；对账查「负责RD = 我，状态 ∈ 待处理 / 验退」，一次捞回所有项目，再按项目号分流。
3b. **合盖暂停、开盖继续**：沿用 bot 合盖规矩；开盖后读通知按断点补读、对账立即跑一轮，「平时 / 测试中」状态与计时接着算（合盖时长不计入「一个工作日」）。
4. **读通知用断点续读**：存「已处理到的消息时间 + id」，每次从断点（往前留 1 秒）按时间正序翻页读到底，按消息 id 去重；建好任务（或确认不用处理）才挪断点；首次开启从开启时刻读起；离线久了照样补读，并私信「补读了 N 条」。
5. **项目群按群 id 绑定，不按群名找**（群名会改、不规范）：bot 进项目群时存「项目号 → 群 id」，换群同步更新，之后回群 / 群操作一律用群 id。替换现在的 `pickChatIdByProject`（按群名匹配）。
6. **领单范围、修改范围、分支策略、回写口径都按仓库配置**，不写死。

## 四、设计

### 4.1 三个入口，一个出口

```text
读通知（平时 60 分钟；测试中 工作时间 1 / 其他 10 分钟）──► 定位记录 ─┐
对账（平时 120 分钟；测试中 15 分钟；所有项目）          ──► 记录 ──────┼─► 一条 bug 一个任务（幂等：记录 id + 状态代）
团队范围（默认关；按 fixScope.pickUp）                ──► 记录 ──────┘
```

- 三个入口都只产出「记录」，去重、建任务、回写走同一条路，现有 `lark-bugtable-poller.mjs` 拆成这三个入口 + 公共的「记录 → 任务」。
- 对账查询条件：负责RD = 我，状态 ∈ 待处理 / 验退（不按项目号过滤）；团队范围打开时把负责人条件换成 `pickUp`。
- `lark-bot poll-on / poll-off / poll-status` 改成切「测试中 / 平时」两档（不再是启停整个轮询器）；状态、进入时间、最后一条新通知时间持久化在 `runtime/`，重启 / 合盖后接着算。
- 合盖：沿用 bot 现有规矩暂停；开盖后读通知按断点补读，对账立即跑一轮。

### 4.2 项目上下文

| 要的东西 | 来源 |
|---|---|
| 项目号 | 通知卡片「需求ID」/ 表「项目ID」列，`safeProject` 校验（只认 `PR-####` / `PM-####`） |
| worktree | 现有逻辑不变：有 `<worktreesDir>/<项目号>` 就用（有 WIP 时从其已提交 HEAD 开隔离分支），没有就临时 worktree |
| 上下文文档 | 现有 PRD 缓存（`prdCacheDocsFor`）+ 记录的评论（bugpoll 的 `comments.py` 搬过来：后端常把契约 / 文档链接写在评论里，Bug-5022 教训） |
| 回哪个群 | **项目 → 群 id 绑定表**（`runtime/lark-project-chats.json`）：bot 被拉进群（`im.chat.member.bot.added_v1`）或首次在群里被 @ 时，按群名提示的项目号私信我确认后写入；我也可以私信「PR-xxxx 群是这个」改绑；没有绑定就私信我，不回落到猜群 |
| 并行 | 同一项目号串行（都要合回同一个项目分支，并行易冲突）；不同项目号并行，受全局并发上限 |

### 4.3 分支策略（`bugFix.branchMode`）

| 值 | 做法 | 谁用 |
|---|---|---|
| `local-commit`（默认，即现状） | 在项目 worktree / 临时 worktree 里改，只本地提交，我来合 | fameex |
| `per-bug-mr` | 从 `bugFix.base` 切 `hotfix-<编号>`，修好推送并建发往 `bugFix.mrTarget` 的 MR；验退且 MR 已合 → `hotfix-<编号>-2` | falive（若 D1 选 b） |

两种模式共用、从 `hotfix.sh` 搬成确定性代码的能力：

- **查重**：开工前按 Bug 号（基线近 14 天、我的开发分支、远端未合分支里写了这个 Bug 号且改了代码的提交）；推送 / 提交前再按 Bug 号 + 本单改过的文件查；近 3 天别的未合分支改过同样文件的只提示。命中 → 不修，表里备注「已由 <提交> 修复」。
- **占用标记**：我在会话里手动修某单时留标记，bot 遇到同单整单跳过；收尾清标记。
- **端口分段**：bot 自测端口 3xxxx / 4xxxx，手动修 5xxxx / 6xxxx，按编号算。
- **收尾核对**：`per-bug-mr` 核对本地与远端一致才删本地分支；不推的收尾保留分支。

### 4.4 修改范围与领单范围（`fixScope`）

```json
"fixScope": {
  "pickUp": { "assignees": ["me"], "ports": ["Web"], "excludePorts": ["App"] },
  "modules": "owned"
}
```

- `pickUp`：团队范围入口领哪些单（`assignees` 填 `me` 或成员 open_id 列表）。
- `modules`：`all`（单里涉及谁的模块都改，负责RD 不变，只备注认领——falive 现在的做法，提示词里要明确写出来覆盖仓库「按负责人改代码」规则）/ `owned`（只改我负责的，别人的部分写清根因和该改哪里，备注里 @ 负责人）/ 成员列表。
- 渲染成提示词里的一句话，不再写死在文案里。
- **11-04 更新**：`modules` 已删（aven 11-04 决策：fameex 没有模块归属表，需求定边界、改码不超界，由 `lib/lark-scope-contract.mjs` 按需求核对），任务正文不再按模块归属限改动。

### 4.5 修复质量门槛（规则块）

把 bugpoll `prompt.md` 3.1 搬成 bug 任务专用规则块：先定根因再动手、同因搜索（按 `change-scoping`）、影响面盘点、改动最小（`git diff <基线>...HEAD` 逐行过）、自测覆盖「没坏别的」、有一项没过就不提交 / 不推。进提示词篇幅预算，用 falive 审计回放核规则零丢失。

### 4.6 回写口径（`bugFix.writeback`）

| 时机 | fameex（现状） | falive 口径（若 D1 选 b） |
|---|---|---|
| 领取 | 状态改「修复中」 | 只追加备注「MM-DD bot 修复中（分支 …）」，不改状态 |
| 完成 | 改 `doneValue`（待推版） | 推 MR 后改「待推版」+ 备注修复说明、自测证据、MR 链接 |
| 部署后 | — | 探到部署改「已推版」 |

### 4.7 bugpoll 其余步骤

- 读评论：并入 4.2，所有仓库都要。
- 验退处理（先读测试复测说明、在环境实测、备注「验退原因」）：并入 bug 任务的提示词，所有仓库都要。
- 分类 / 分配负责人 / 改端口、群里要账号：属于团队范围入口的活，`pickUp` 打开时才带；fameex 默认不带。

### 4.8 出错开工单自修（aven 11-01 加）

lark-bot 已有自修工单（`lib/lark-self-fix*.mjs`，port 台账 #36–#39）：worker 任务失败 → 指纹归类 → 复发或未归类开单（同指纹去重、每天最多 3 张）→ 空闲时在临时 worktree 让 claude 查根因、只在 harness / prompt 层才改 → 机械验收（改动只许 `lib/ scripts/ __tests__/ docs/`、全量单测绿、变异存活 0）→ 本地提交、私信我 → `lark-bot self-fix apply` 合进运行分支。

- **bug 任务本身**（worker 里修 bug 失败）：直接走现有流程，不用改。
- **新入口的失败要接进来**：读通知、对账、按标题定位记录、断点读写、项目群绑定、表格回写都跑在轮询进程里，不经过 worker 的失败台账。改成：失败统一用 `fingerprintFailure` 归类，记进同一本失败台账；`maybeOpenSelfFix` 支持「无任务」工单——工单附入口名、轮询日志尾 150 行、当时的状态（平时 / 测试中、断点位置）、出错那版 HEAD，其余（执行器、验收、apply）完全复用。
- **只告警不开单**：外部原因（Lark 接口限流 / 网络抖动 / 我的用户身份失效 / 表格权限）归 `external` / `env`，按现有剧本只告警；同一入口连续失败 3 轮私信一次（沿用轮询器 `errorAlertRounds`）。
- **自修边界不变**：不碰 `runtime/`（断点、绑定表、状态文件），状态文件损坏按「六、风险」的兜底处理，不交给自修改。

## 六、风险与回退

- **用我的身份读私聊**：只读 `+chat-messages-list`，不发消息；身份失效（refresh token 7 天不用会过期）时读通知入口告警并停，对账照跑。
- **标题定位记录误配**：多条 / 0 条一律私信我，不猜。
- **断点损坏**：断点文件原子写；读不出时从「当前时刻 − 24 小时」重读一遍并去重，私信一句。
- **回退**：每批有配置开关（`bugWatch.enabled`、`bugFix.branchMode`、`fixScope`），关掉即回到现状；B2 上线前保留旧轮询器代码，确认一周后删。
