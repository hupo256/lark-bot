# falive case 实跑方案 v2（定稿 11-04）

> 目标：用最新 lark-bot 把 falive-bot 做过的 285 个 case 读全上下文跑一遍，和 falive 当时逐条比，找出真问题修掉；每修一处都能快、准、省 token 地再验，直到达到验收标准（§6）后合进运行分支。
> 本文是方案定稿；执行进度记在 [falive-replay-plan-2026-11-03.md](falive-replay-plan-2026-11-03.md)，交接说明在 [handoff-falive-replay-2026-11-04.md](handoff-falive-replay-2026-11-04.md)。

## 0. 前提（实测）

| 事实 | 数 | 含义 |
|---|---|---|

## 1. 为什么换掉「按天切段」

1. 一段几天、几百条消息，任何一处坏了整段重来；跨段的事接不上；断点只能精确到一天。
2. 每轮全量真跑：改一行分类提示，也要把 285 个 case 的执行（改代码、实测）全部重跑一遍。
3. 每轮全量裁判：输出没变的也重判，结论随模型抽样来回摆，分不清是代码变了还是抽样变了。
4. 模拟器没校准过：分不清「lark-bot 做得不好」和「模拟器没还原当时的场景」。

## 2. 单位：事件组

- **分组规则**（`scripts/sim/episodes.mjs` → `replay/falive/episodes.json`，进版本）：
  1. 同话题、回复链、消息里引用的任务 id（含 aven 私聊里「继续任务 / 就这样回」指向的任务）在同一组。
  2. 同一个群或私聊里，相邻两条 case 间隔小于 30 分钟并组。lark-bot 判「是不是接着上一件事」会看同群最近的任务，拆开就测不到并错 / 该并没并。
  3. 用 falive 当时真实发生的归并 / 续跑（审计与网关日志）校验：falive 并过的两条必须在同一组，不在就并组。
  4. 同一天、同一功能、都是改代码的 case 并组：组与组的业务仓不共享，拆开后一组看不到前一组改的代码。
- **每组单独起一个 lark-bot 实例**：从组里第一条消息前 30 分钟开始，到最后一条之后 bot 没有动静为止。组内消息按真实间隔喂，bot 状态（任务、义务、草稿）连续，跨天的组照样跨天，每天换业务仓基线。
- **组外的群聊照样是上下文**：假 lark-cli 按虚拟时钟供应全部真人消息；**组外的 bot 消息供 falive 当时的原话**，因为人后面的话是在回应那句。
- **断点精确到组**：每组跑完，把结果（发件、任务、审计）连同代码指纹存进 `results/<组>/`；中断后只补没跑完的组。

## 3. 分层：先便宜的，再贵的

| 层 | 跑什么 | 花多少 | 什么时候跑 |
|---|---|---|---|
| L1 接话层 | 285 条只跑分类 / 归并 / 「收到」那一步，不执行 | 285 次分类调用 | 每次改动先跑，几分钟出结果 |
| L2 对话层 | 事件组整段跑，执行层走录放（§4） | 只花「输入变了」的调用 | 改了路由 / 交付 / 提示词 |
| L3 真执行 | 执行层也真跑 | 最贵 | 受影响的组；全量基线一次；合并前一次 |

## 4. 录放：同样的输入不再花第二次钱

- **录**：每次真调用 Claude，按「去掉每次都变的部分（任务 id、虚拟时间、临时路径）后的完整输入」做指纹，把输出存下来。雏形是 `scripts/sim/claude-cache.mjs`，没在整轮里验证过。
- **放**：下一轮同样的输入直接放录好的输出，不花 token、立刻出结果、可复现，裁判看到的差异一定来自代码。
  - 只读调用（分类、分诊、答疑、实测）输入一样就放。
  - 改代码的调用还要求业务仓状态完全一致才放。
- **别预设能省多少**：改 worker 提示词（最常见的修复之一）会让所有执行调用都不命中；录放主要省「只改了分类 / 路由 / 交付」的轮次。启用前先实测：同一组跑两遍，第二遍只读调用命中 ≥ 90%、输出一致。

## 5. 按影响重跑、裁判与金标准

**按影响重跑**：
- 每组跑的时候记下走过的环节：分类、归并、执行模式、交付出口。
- 第一版按层粗分：
  - 改分类 / 接话 → L1 全量 + 全部组的接话；
  - 改 worker 提示 → 所有走该模式的组；
  - 改交付 → 所有有回复的组。
- 每次另加 **20 组固定的金丝雀**防回归。全量只在基线和合并前各跑一次。

**裁判**：
1. **规则预判**（不花 token）：回没回、回了几条、有没有重复、多久回、任务终态、交付物类型。和上一轮一样就沿用结论。
2. **模型只判有变化的**：lark-bot 输出指纹和上次判过的不同才送模型。用 Opus，**平时 effort high；定金标准前那一轮全量裁判用 max**（只判一次）。
3. **裁判提示冻结、进版本**：每轮记在 `rounds/<轮>/code.txt`。改了裁判提示，就重判金标准涉及的 case，新旧结论不混着比。

**金标准**：
- 全量裁判（max）后，「falive 更好 / 都不对 / 裁判拿不准」的 case（估 30–60 条）由 **aven 亲自过**，定成 `replay/falive/gold.jsonl`。
- 之后都对照金标准判。

**实测类 case**（环境还原不了：实测打到的是今天的 pre / OL，不是当时的）：
- 先从 falive 审计里取当时的实测证据（接口返回、页面现象），标出这类 case。
- 裁判看过程（测没测、测的对象和方法对不对），不看「通没通」。
- 当时环境挂了 / 现在挂了的单独标。

## 6. 验收标准（aven 11-04 同意）

合进运行分支的门槛，对照金标准判：
- **硬线**：
  - 涉及钱 / 状态 / 权限 / 不可逆操作的 case 不能有「lark-bot 更差」。
  - 不能有新出现的重复回复、该回没回、回错人。
- **总体**：「falive 更好」不超过 285 条的 5%（≤ 14 条），每一条都有已知原因（模拟局限 / 待办 / 已记录的后续改进）。
- **不回退**：后一轮不能把前一轮已判「一样 / lark-bot 更好」的 case 变差。

## 7. 已定的口径（aven 11-04）

| 事 | 口径 |
|---|---|
| 「已部署」→ 自动复测 | 待办，不搬（fameex 的 CI/CD 不一样，以后再接）；这类 case 标「待办，不计分」 |
| 改码边界 | fameex 不要模块归属表；**需求要定边界、改码不超界**。裁判按「有没有超出需求边界」判 |
| 实测发 POST 登录 | 允许：为登录拿态的 POST 可以发，其余写操作仍禁止 |
| 「能不能先打包到 uat / OL」 | 按回答处理 |
| 云文档 / bug 单版本 | 用拉取时的版本，不纠结当时版本 |
| 录放 | 只读调用输入一样就放；改代码的调用要业务仓状态完全一致 |
| 汇报 | 每个阶段做完先向 aven 报结果，再进下一阶段；一轮作废先报告再重跑 |

## 9. 闸与守卫（已有，沿用）

- **预检** `preflight.mjs`：数据齐、代码干净且含 fameex-stable 全部提交、环境通；不过不跑。
- **冒烟**：核对 bot 实际看到的上下文与原始群聊一致。
- **止损守卫** `round-guard.mjs`：进程崩溃、读取缺口、分类失败 ≥ 3、长时间不动即停；改守卫规则先用历史日志 `--once` 验证。
- **额度闸** `claude-q`：撞限额冻时钟、到点重试。
- **作废先报告**。

## 10. 已知局限

- 组与组并行时，bot 的全局排队（worker 并发）和「同一个人 2 分钟内只回一条」这类全局闸不完全还原；30 分钟并组已覆盖同群挨着的情况，剩下的在裁判里标「模拟局限」。
- 实测类 case 的环境还原不了，按 §5 判过程不判结论。
- 云文档 / bug 单是拉取时的版本。
- 跨组的业务仓改动看不到，靠 §2 规则 4 并组缓解。
