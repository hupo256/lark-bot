# falive case 实跑方案 v2（11-03 晚，替代「按天切段」的跑法）

> 目标：用最新 lark-bot 把 falive-bot 做过的 285 个 case 读全上下文跑一遍，和 falive 当时逐条比；之后每修一处能快速、便宜、可信地再验。
> 本文是设计，执行进度仍记在 [falive-replay-plan-2026-11-03.md](falive-replay-plan-2026-11-03.md)。

## 0. 现在的约束（实测）

| 事实 | 数 | 含义 |
|---|---|---|
| case | 285 条（@bot 181、回复 bot 61、aven 私聊 43），时间线 4152 条 | 不触发 bot 的消息只是上下文，不花 token |
| 按「事」分组（同话题 / 回复链 / 引用任务 id / 同人同群 15 分钟内连发） | **142 组**：单条 92、2–3 条 34、4–8 条 12、9 条以上 4（最大 19 条）；跨天的只有 5 组 | 组与组之间互不依赖，可以各跑各的 |
| 执行成本（r11 前 1/3 的 132 次 worker 调用） | 合计约 $87 等价，中位 $0.33、p90 $1.95；**最贵的 20% 调用占 59%** | 钱花在少数长执行任务上，省 token 要先省它们 |
| 瓶颈 | Claude 账号 5 小时窗口额度，与线上 bot 共用 | 并行再多也快不过额度；必须少花、花在刀刃上 |

## 1. 旧跑法的毛病（为什么要换）

1. **按天切段**：一段几天、几百条消息，任何一处坏了整段重来；跨段的事接不上；断点只能精确到「一天」。
2. **每轮全量真跑**：改一行分类提示，也要把 285 个 case 的执行（改代码、实测）全部重跑一遍，最贵的那 20% 调用每轮都花。
3. **每轮全量裁判**：输出没变的 case 也重判，裁判结果还会因为模型随机性来回摆，分不清是代码变了还是抽样变了。
4. **模拟器本身没校准过**：分不清「lark-bot 做得不好」和「模拟器没还原当时的场景」。

## 2. 新方案：以「事件组」为单位，分层、录放、按影响重跑

### 2.1 单位：事件组（episode），不是「天」

- 用上面的规则把 285 个 case 并成 142 个事件组（`scripts/sim/episodes.mjs` 生成 `replay/falive/episodes.json`，进版本）。另外把 aven 私聊里「继续任务 / 就这样回」指向的任务并进被指的那组。
- **每组单独起一个 lark-bot 实例**：从组里第一条消息前 30 分钟开始，到最后一条之后 bot 没有动静为止。组内消息按真实间隔喂、bot 状态（任务、义务、草稿）连续，跨天的组照样跨天。
- **组外的群聊照样是上下文**：fake lark-cli 按虚拟时钟供应全部真人消息，**组外的 bot 消息供 falive 当时的原话**（人后面的话是对 falive 那句的反应，换成空白就失真）。
- **断点续跑精确到组**：每组跑完把结果（发件、任务、审计）连同代码指纹存进 `results/<组>/`；中断后只补没跑完的组，最多丢正在跑的那几组。

### 2.2 分层：先便宜的，再贵的

| 层 | 跑什么 | 每次花多少 | 什么时候跑 |
|---|---|---|---|
| L1 接话层 | 285 条只跑分类 / 归并 / 「收到」那一步，不执行 | 285 次分类调用（便宜） | 每次改动都先跑，几分钟出结果 |
| L2 对话层 | 事件组整段跑，执行层用**录放**（见 2.3） | 只花「输入变了」的调用 | 改了路由 / 交付 / 提示词 |
| L3 真执行 | 执行层也真跑 | 最贵 | 只对受影响的组；合并前一次 |

### 2.3 录放：同样的输入不再花第二次钱

- 每次真调用 Claude，按「规范化后的完整输入」（参数 + 提示 + 附件内容 + 业务仓状态）做指纹，把输出存下来（`scripts/sim/claude-cache.mjs` 已有雏形，未在整轮验证过）。
- 下次输入一模一样就直接放录好的输出：**不花 token、秒回、结果可复现**。只读调用（分类、分诊、答疑、实测）能放；改代码的调用只有业务仓状态完全一致才放。
- 好处不止省钱：裁判看到的差异一定来自代码，而不是模型这次抽样不一样。
- 上线前先验：同一组跑两遍，第二遍命中率、输出一致性达标才启用（`claude-cache-check.mjs`）。

### 2.4 按影响重跑：改哪儿跑哪儿

- 每组跑的时候记下它走过哪些环节：分类、归并、哪种执行模式、交付出口、用了哪段提示。
- 一次修复按 `git diff` 触到的文件 / 提示段，挑出走过这些环节的组重跑，再加一份**固定的金丝雀组**（20 组，覆盖各类场景）防回归。
- 全量只在合进运行分支前跑一次，而且有录放，没变的部分不花钱。

### 2.5 裁判：先规则、后模型、按差异判

1. **规则预判（不花 token）**：回没回、回了几条、有没有重复、多久回、任务终态、交付物类型。和上一轮已判的结果一样就沿用结论。
2. **模型只判有变化的**：本轮 lark-bot 输出的指纹和上一次判过的不同，才送模型裁判。判过的按 `(case, 输出指纹)` 缓存。
3. **金标准**：第一轮全量裁判后，只把「falive 更好 / 都不对」和裁判拿不准的给 aven 过一遍，定成金标准（`replay/falive/gold.jsonl`）。之后对照金标准判，结论不再来回摆。

### 2.6 先校准模拟器：分清「bot 不行」和「模拟不像」

- 用 falive 自己的代码（`~/github/lark-bot-falive`）在模拟器里跑 20 个事件组，和 falive 当时真实的表现比。
- 两边应当基本一致；对不上的地方就是模拟器还原不了的（缺上下文、时序、环境），修模拟器或在裁判里标「模拟局限」。不做这一步，后面所有「lark-bot 更差」都可能是模拟器的锅。

### 2.7 快：按额度调度，而不是按段数

- **额度调度器**：从每次调用结果里读实际花费，按 5 小时窗口算消耗速度；回放最多用窗口的 70%，留 30% 给线上 bot。快到上限就降并发；真撞了限额，额度闸冻住时钟、到点重试（已有）。
- **排队顺序**：先跑本次修复直接针对的组（最快拿到反馈），再跑金丝雀，最后其余；同优先级里最长的组先跑（最长的 19 条组不拖尾）。
- 事件组都小，并发可以开到额度允许的上限，不再受「8 段」的结构限制；机器负载另设上限（负载过高会把 bot 的节奏拖慢，影响准确性）。

### 2.8 闸与守卫（已有，沿用）

预检（数据齐、代码干净且最新、环境通）→ 冒烟（抽 3 组，核对 bot 实际看到的上下文与原始群聊一致）→ 止损守卫（进程崩溃、读取缺口、分类失败、长时间不动即停）→ 作废先报告。

## 3. 执行步骤与成本估计

| 步 | 内容 | Claude 花费 | 墙钟 |
|---|---|---|---|
| P0 | 事件组切分、规则预判、录放命中率验证、按影响选组的记录点 | 几乎为 0（命中率验证跑 2 组） | 半天 |
| P1 | 模拟器校准：falive 代码跑 20 组 | ≈ 1/10 窗口 | 1–2 小时 |
| P2 | 最新代码全量跑 142 组（L2 + 真执行，同时录下所有调用） | ≈ 2–3 个窗口（一轮的成本，只此一次） | 按额度 10–15 小时，可断点 |
| P3 | 全量裁判 + aven 过一遍分歧 → 金标准 | ≈ 285 次裁判；aven 约 30–60 条 | 2 小时 + aven 时间 |
| P4 | 迭代：修 → L1 全量 → 受影响组 + 金丝雀（录放） → 按差异裁判 | 每次多数是录放命中，只花改动涉及的那部分 | 每次几十分钟 |
| P5 | 合并前：全量（录放）+ 未命中的真跑 + 裁判 | 只花未命中部分 | 几小时 |

## 4. 已知局限（写明，不装看不见）

- 组与组并行时，bot 的全局排队（worker 并发）与「同一个人 2 分钟内只回一条」这类全局闸，在分组跑时不完全还原；同一时段、同一群的组如果有这种交互，并进同一组跑。
- 业务仓按天钉基线，组内跨天照样每天换基线。
- 云文档 / bug 单是拉取时的版本，不是当时的版本（aven 已定：不纠结版本）。
- 环境（pre / OL 的真实状态）无法还原，实测类 case 的「环境当时能不能用」以 falive 当时的记录为准，裁判里单独标出。
