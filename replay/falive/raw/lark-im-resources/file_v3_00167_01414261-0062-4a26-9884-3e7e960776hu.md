# PRD 模板（AI 自测友好版）

Oct 6, 2026 · @Rou

这份模板规定 PM 如何编写 falive-react 各功能的 PRD，使每个功能点都能被 AI 直接转化为可执行的测试用例。核心原则一条：每条需求都必须**可定位、可量化、有唯一确定的预期结果**——凡是 AI（或任何人）读完无法判断「通过还是不通过」的描述，都要改写或补全。

## 1. 怎么用这份模板（给 PM）

这份模板不是要你多写字，而是把你脑子里「做成什么样才算对」落成 AI 能逐条核对的文字。写法只有一条判断线：**如果 AI 读完这句话，不打开你的脑子就能唯一判断「通过 / 不通过」，这句话就合格；否则必须改写或补数据。**

怎么组织：

1. 每个模块一份 PRD，按「文档头 → 通用规则 → 功能点清单 → 逐功能点规格」四段写（见第 3 节）。
2. 每个功能点复制一次「单功能点规格模板」（第 7 节）填写，一个都不省。
3. 写完对照第 12 节自检清单逐条打勾，再提交。

贯穿全文的核心原则 —— **可定位、可量化、有唯一确定预期**：

- **可定位**：AI 能找到你说的那个元素 / 页面 / 接口。给出路由路径、`data-testid`、按钮文案或接口地址，而不是「那个按钮」。
- **可量化**：预期用具体值、范围或精确文案表达，不用「快」「友好」「合理」「正常」这类无法验证的词。
- **有唯一确定预期**：同一个操作，预期结果只能有一个，不随读者理解而变。如果一个场景有多种合理结果，说明你漏了前置条件，补上。

## 2. AI 自测友好的黄金规则

每条规则都是为了让 AI 能把 PRD 一句话直接变成一条测试用例。表右两列是同一件事的反例与正例。

| # | 规则 | 为什么 | 反例（别这样） | 正例（这样写） |
| --- | --- | --- | --- | --- |
| 1 | 每个功能点有唯一 ID | 用例能 1:1 映射回需求，跟踪不丢 | 「登录功能」 | `FN-LOGIN-001` 登录表单提交 |
| 2 | 验收标准结构化 | 前置/操作/预期三段可直接转用例 | 「点登录能正常登录」 | 已输正确账密 → 点登录 → 1s 内跳转 `/home` 且右上角显示用户名 |
| 3 | 输入输出具体化 | AI 需要真实可填的值 | 「输入合法手机号」 | 合法：`13800138000`；非法：`1380013800`（11 位以外） |
| 4 | 结果可观测 | 必须是页面/接口/状态能看到的 | 「用户感觉流畅」 | Toast 显示「登录成功」且 2s 后自动消失 |
| 5 | 元素稳定可定位 | AI 要能找到元素 | 「点那个蓝色按钮」 | 按钮文案「登录」，`data-testid="login-submit"` |
| 6 | 列全边界与异常 | 负向用例占自测一半 | 只写成功路径 | 空输入、超长、错密码、断网、账号锁定各列预期 |
| 7 | 文案精确到字 | AI 要做文本断言 | 「提示密码错误」 | 标题「登录失败」，正文「账号或密码错误」（逐字） |
| 8 | 标优先级 P0/P1/P2 | AI 知道哪些必须过 | 不分主次 | `P0` 阻断发布；`P2` 体验优化 |
| 9 | 明确「不做」范围 | 避免 AI 误报未实现的点 | 不写 | 本期不做「记住我」与第三方登录 |
| 10 | 前置数据与账号明确 | AI 需要可复现的环境 | 「用测试账号」 | 账号 `qa_user01` / 密码 `Test@1234`，角色普通用户 |

## 3. 一个模块 PRD 的整体结构

每个模块（如登录、订单、个人中心）的 PRD 按这四段写，顺序固定：

1. **文档头 — 模块元信息**（第 4 节）：这个模块是什么、在哪、依赖什么、用什么账号和环境测。
2. **通用 / 全局规则**（第 5 节）：本模块所有功能点共用的规则（错误提示、加载态、未登录跳转等），写一次，后面功能点直接引用，不重复。
3. **功能点清单总表**（第 6 节）：把模块拆成一条条可独立自测的原子功能点，每条一个 ID。这张表是 AI 跑自测的「总清单」。
4. **逐功能点规格**（第 7 节模板）：清单里每个功能点展开写一份详细规格。

**ID 命名约定**（全项目统一，AI 靠它做映射）：

- 功能点：`FN-<模块>-<三位序号>`，如 `FN-LOGIN-001`。
- 验收标准：在功能点下编号 `AC-01`、`AC-02`，全路径即 `FN-LOGIN-001 / AC-03`。
- 异常 / 边界场景：`EX-01`、`EX-02`。

> 建议：模块多时，每个模块单独一份 PRD（或一个标签页），辙文档头和通用规则只写本模块的。

## 4. 文档头 — 模块元信息模板

每份模块 PRD 开头复制这张表并填满。空着不填的字段会让 AI 无法搭建可复现的测试环境。

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| 模块名称 | 业务模块名 | 登录与鉴权 |
| 模块 ID 前缀 | 本模块功能点统一前缀 | `FN-LOGIN-*` |
| 版本 / 日期 | PRD 版本号与更新日期 | v1.2 / 2026-10-06 |
| 负责 PM | 可追问的人 | 张三 |
| 关联设计稿 | Figma / 设计链接（精确到画板） | [登录画板](https://…) |
| 关联接口文档 | Swagger / Apifox 链接 | [认证 API](https://…) |
| 涉及路由 | 本模块所有前端路由路径 | `/login`、`/forgot-password` |
| 依赖模块 | 必须先存在才能测本模块的前置 | 用户中心（提供账号） |
| 测试环境 | 自测跑在哪个环境 | 语境 test：`https://test.falive.…` |
| 测试账号 | 可直接登录的账号、密码、角色 | `qa_user01` / `Test@1234` / 普通用户；`qa_admin` / `Test@1234` / 管理员 |
| 需要的测试数据 | 预先造好的数据前置 | 已存在 1 个已锁定账号 `locked_user` 用于锁定场景 |
| 浏览器 / 端 | 支持范围（影响兼容性用例） | Chrome 最近两个大版本、移动端 H5 |

## 5. 通用 / 全局规则模板

这些规则全模块共用,写一次。功能点里只要写「遵循全局规则 G-03」就行,不用每次重写。每条给一个 ID(`G-01`…)便于引用。下表是常见项,按项目实际填写具体值。

| ID | 场景 | 统一规则(填具体值) |
| --- | --- | --- |
| G-01 | 错误提示样式 | 统一用顶部 Toast,停留 2s 自动消失;表单校验错误在字段下方红字显示 |
| G-02 | 加载态 | 请求超过 300ms 未返回显示 loading;提交按钮置灰禁点,防止重复提交 |
| G-03 | 空态 | 列表无数据时显示统一空态图 + 文案「暂无数据」 |
| G-04 | 未登录 / 登录过期 | 访问需登录页面时跳转 `/login` 并带 `redirect` 参数;登录后回到原页 |
| G-05 | 权限不足 | 无权限访问时跳 403 页或 Toast「无访问权限」,不暴露数据 |
| G-06 | 网络 / 服务器异常 | 5xx 或断网时 Toast「网络异常,请稍后重试」,页面保持原状不白屏 |
| G-07 | 分页 | 每页默认 20 条;翻页保留筛选条件;最后一页不显示「下一页」 |
| G-08 | 表单必填 | 必填项标红星 `*`;未填点提交时定位到第一个错误项并提示 |
| G-09 | 二次确认 | 删除 / 不可逆操作弹确认框,文案「确定删除?此操作不可恢复」 |
| G-10 | 金额 / 时间格式 | 金额保留 2 位小数、千分位;时间统一 `YYYY-MM-DD HH:mm` |

> 功能点规格里的「预期结果」若与某条全局规则一致,直接写 `见 G-06`,不要复制整段。

## 6. 功能点清单总表模板

把模块拆成一条条**可独立自测的原子功能点**。拆分粒度的标准：一个功能点 = 一条「用户在某入口完成某件事」，能单独给出通过/不通过。过大（如「用户管理」）要拆，过小（如「按钮变色」）归到验收标准里。

| 功能点 ID | 名称 | 优先级 | 入口 / 路由 | 一句话描述 | 依赖 | 验收标准数 |
| --- | --- | --- | --- | --- | --- | --- |
| FN-LOGIN-001 | 账密登录 | P0 | `/login` | 输入账号密码登录并进入首页 | 用户中心 | 6 |
| FN-LOGIN-002 | 表单校验 | P0 | `/login` | 账号/密码格式与必填校验 | - | 5 |
| FN-LOGIN-003 | 忘记密码 | P1 | `/forgot-password` | 通过验证码重置密码 | 短信服务 | 4 |

填写要点：

- **优先级**：`P0` 阻断发布（主流程、核心校验）；`P1` 重要但有替代；`P2` 体验优化。AI 优先保 P0 全通。
- **入口 / 路由**：写精确路径，有参数的给示例（`/order/:id`）。
- **验收标准数**：该功能点在第 7 节里写了几条 AC，用于最后对账有没有漏写。

## 7. 单功能点规格模板（核心）

这是整份模板的重心。\*\*每个功能点复制下面这套字段填一遍。\*\*先看每个字段的含义与对 AI 的作用，再用最后的空白模板填写。

| 字段 | 怎么填 | 对 AI 自测的作用 |
| --- | --- | --- |
| 功能点 ID / 名称 | 与清单一致 | 用例映射的锚点 |
| 优先级 | P0/P1/P2 | 决定必过还是选过 |
| 入口与路径 | 怎么到达这个功能（路由 + 点哪里进入） | AI 导航到起点 |
| 前置条件 | 测这个功能前必须成立的状态：用什么账号/角色、已有什么数据、在哪个页 | AI 搭建可复现环境 |
| 页面元素清单 | 表格列出每个元素：名称、类型、定位（文案或 `data-testid`）、默认状态 | AI 找得到、点得中 |
| 操作流程 | 编号步骤，一步一个动作 | AI 按步回放 |
| 验收标准 AC | 每条用 Given-When-Then（第 8 节），编号 AC-01… | 每条 = 一个测试用例 |
| 输入与校验 | 每个输入字段的规则、合法/非法样例、边界值（第 9 节） | AI 生成正/负用例 |

| 非功能要求 | 性能阈值、响应式断点、兼容性、无障碍（能量化的才写） | AI 做可量化断言 |

## 8. 验收标准写法（Given-When-Then）

每条验收标准都用三段式，AI 能把它直接当成一个测试用例跑：

- **Given（前置）**：做这个操作前，系统处于什么状态（账号、数据、所在页）。
- **When（操作）**：用户做了一个明确动作（输入什么、点什么）。
- **Then（预期）**：系统给出的**可观测**结果（跳哪、显什么文案、数据怎么变）。

一条 AC 只验一件事。若 Then 里出现「并且」好几件不相关的事，拆成多条。

可测与不可测对照：

| ✖ 不可测（别这样） | ✔ 可测（改成这样） |
| --- | --- |
| 登录成功后进入首页 | 【Given】已输正确账密 `qa_user01/Test@1234`【When】点「登录」【Then】≤ 1s 跳转 `/home`，右上角显示 `qa_user01` |
| 密码错误有提示 | 【Given】账号存在、密码错【When】点「登录」【Then】停留登录页，Toast「账号或密码错误」，不跳转 |
| 列表加载很快 | 【Given】列表有 20 条数据【When】进入页面【Then】首屏 2s 内渲染完，出现 20 行 |
| 金额显示正确 | 【Given】订单小计 1234.5【When】进入详情【Then】显示 `¥1,234.50` |

写不出具体 Then 的时候，往往是这个点本身没想清楚——这正是需要 PM 补齐的地方。

## 9. 输入校验与边界 / 异常场景清单

负向用例占自测的一半。每个输入字段和每个交互都要把「出错的情况」列全，否则 AI 只会测成功路径。

### 9.1 每个输入字段要写的

用下表把每个字段写清楚：

| 字段 | 必填 | 规则（长度/格式/范围） | 合法样例 | 非法样例 | 非法时提示（逐字） |
| --- | --- | --- | --- | --- | --- |
| 手机号 | 是 | 11 位数字，1 开头 | `13800138000` | `1380013800`、`abc` | 请输入正确的手机号 |
| 密码 | 是 | 8–20 位，含字母+数字 | `Test@1234` | `123`（太短） | 密码需 8–20 位且含字母与数字 |

### 9.2 每个字段必须覆盖的边界值

按这个清单逐条过（带长度/数值限制的字段尤其）：

- 空值 / 只输空格
- 最小值、最小值-1、最大值、最大值+1（长度或数值）
- 特殊字符、emoji、空格在首尾
- 大小写 / 前后空格是否敏感
- 粘贴超长文本、HTML/脚本注入（`<script>`）

### 9.3 每个功能点必须覆盖的异常分支

下列能编号成 EX-01…写进功能点规格，每条给「触发条件 + 预期」：

| 场景 | 典型预期（按项目调） |
| --- | --- |
| 重复提交 / 连点 | 按钮置灰或只生效一次，不重复请求 |
| 请求进行中切页 / 返回 | 不报错、不残留 loading |
| 接口超时 / 5xx | 见 G-06 Toast，可重试 |
| 接口返回空 / null | 显示空态，不白屏、不报 JS 错 |
| 登录态过期 / 401 | 见 G-04 跳登录 |
| 权限不足 / 403 | 见 G-05 |
| 并发：两端改同一数据 | 明确以谁为准 / 提示冲突 |
| 金额/数量边界：0、负数、最大 | 按规则拦截或正常处理 |
| 刷新 / 前进后退 | 状态不丢（或明确回到哪） |

## 10. 接口依赖模板

功能点调的每个接口都按这个格式写。有了这些，AI 既能做接口层断言，也能判断前端对各种返回的处理对不对。若已有 Swagger/Apifox，可直接贴链接 + 补下面的「业务错误码 → 前端表现」表。

每个接口写：

- **名称 / 用途**：登录
- **方法 + 路径**：`POST /api/auth/login`
- **触发时机**：点「登录」按钮
- **请求体**：`{ "username": string, "password": string }`
- **成功响应（200）**：`{ "code": 0, "data": { "token": string, "userName": string } }`
- **关键字段含义**：`token` 存 localStorage；`userName` 显示在右上角

状态码与业务错误码 → 前端表现（AI 靠这张表做断言）：

| HTTP / code | 含义 | 前端预期表现（逐字文案） |
| --- | --- | --- |
| 200 code=0 | 成功 | 跳 `/home`，存 token |
| 200 code=1001 | 账密错误 | 停留，Toast「账号或密码错误」 |
| 200 code=1002 | 账号被锁 | Toast「账号已锁定，请 15 分钟后重试」 |
| 401 | 未登录/过期 | 见 G-04 跳登录 |
| 403 | 无权限 | 见 G-05 |
| 5xx / 超时 | 服务异常 | 见 G-06，可重试 |

> 若某返回前端行为未定（比如 code=1002 该不该跳转），说明 PRD 还没想到这个分支，补上。

## 12. PM 提交前自检清单 + 模糊词对照

### 12.1 提交前逐条打勾

- [ ] 每个功能点有唯一 ID，且清单总表与详细规格一致
- [ ] 每个功能点标了优先级（P0/P1/P2）
- [ ] 每条验收标准都是 Given-When-Then，Then 可观测（能看到或查到）
- [ ] 每个输入字段都有合法样例、非法样例、边界值、逐字错误提示
- [ ] 每个功能点有异常/边界场景（EX），不只写成功路径
- [ ] 元素有稳定定位（文案或 `data-testid`），没有「那个按钮」
- [ ] 文案、跳转路径、数值都是具体值，没有「快」「友好」「合理」
- [ ] 接口列了状态码/错误码 → 前端表现对照
- [ ] 文档头的测试账号、环境、前置数据都填了，且真实可用

### 12.2 模糊表述 → 可测改写

看到左边的词就要警惕，按右边改成具体值：

| 模糊表述 | 怎么问自己 | 可测改写 |
| --- | --- | --- |
| 响应快 / 加载快 | 多少 ms？ | 首屏 2s 内渲染；请求 P95 < 800ms |
| 用户友好 / 体验好 | 具体看到什么？ | 空态显示图 + 文案「暂无数据」 |
| 正确显示 | 显示成什么格式？ | 金额显示 `¥1,234.50` |
| 有提示 / 给提醒 | 哪种提示、什么文案？ | Toast「账号或密码错误」，2s 消失 |
| 处理异常 / 容错 | 哪些异常？各自怎样？ | 列出 401/403/5xx/空数据各自预期 |
| 支持移动端 | 哪些断点？ | 375px 不横向滚动；≤768px 折叠侧边栏 |
| 权限控制 | 谁能看、谁不能？看不到时怎样？ | 普通用户访问 `/admin` → 403 页 |
| 支持批量 | 上限多少？超了怎样？ | 最多选 50 条，超出 Toast「最多选 50 条」 |

全部功能点按这份模板写完后，AI 就能把每个模块的清单 × 每条 AC/EX 展开成一条条可执行用例，逐一跑自测并回填结果。
