# 社区发帖、Live 关注任务：前端完成申报接入说明

更新日期：2026-10-26。

**业务操作成功后，由前端调用 Go 任务完成接口；Go 负责记录任务、请求 Discuz 发积分及失败补偿。**

> 实现状态：当前 Go 代码已允许 `DAILY_PUBLISH_SQUARE_POST` 和 `FOLLOW_ANCHOR` 前端申报。接入前需确认目标环境已部署包含本次变更的版本，并完成同一任务旧发奖来源的切换。代码支持不等于线上已部署或实际积分已验收。

## 1. 两类任务的调用顺序

| 任务 | 前端业务操作 | 何时申报 | 任务类型 `taskType` |
| --- | --- | --- | --- |
| 社区发帖 | 调用现有社区发帖接口 | 前端确认本次发帖完成后 | `DAILY_PUBLISH_SQUARE_POST` |
| 关注主播 | 先调用 Live `POST /api/member/attention` | 业务成功且操作后 `is_followed = 1` | `FOLLOW_ANCHOR` |

### 1.1 社区发帖

```text
用户提交帖子
  → 调用现有社区发帖接口
  → 前端根据业务响应确认本次发帖完成
  → 获取/刷新 Go 任务列表，匹配未完成的发帖任务
  → POST Go /api/points/task/complete，提交 taskId
  → 刷新任务状态、积分余额和流水
```

- 在发帖成功回调中申报，不是在点击发布、上传附件完成或打开帖子页面时申报。
- 发帖失败、取消发布、保存草稿不申报；不能仅凭 HTTP 200 判断业务成功。
- 发帖接口、参数及业务成功判断沿用现有社区接入约定。
- **审核口径需确认**：若接口提交成功但帖子待审核，是否算任务完成，需要产品和后端上线前明确；不要自行把“提交成功”等同“审核通过”。本说明不改变既有社区积分只对已发布帖子发放的规则。

### 1.2 Live 关注

```text
用户发起关注
  → POST Live /api/member/attention，提交被关注主播的 Live 用户 id
  → 确认 code = 0，且业务数据中的 is_followed = 1
  → 获取/刷新 Go 任务列表，匹配未完成的关注任务
  → POST Go /api/points/task/complete，提交 taskId
  → 刷新任务状态、积分余额和流水
```

- Live 请求沿用现有 Live 域名、鉴权、公共签名和响应解密封装；业务成功码是 `0`，但必须同时检查操作后的关注状态。
- 关注失败、取消关注、页面初始化显示“已关注”不申报。
- 此接口明确采用关注/取关切换逻辑：未关注时调用会关注，已关注时调用会取消；不能只因 HTTP 200 或 `code = 0` 就申报。
- 本次不额外调用 Go `/api/b2b/follow` 或 Java 关注接口，不双写关注。任务申报不会创建或同步 Live/HiChat 关注关系。

### 1.3 Live 关注接口 API 明细

| 项目 | 说明 |
| --- | --- |
| 接口路径 | `/api/member/attention` |
| 请求方法 | 前端使用 `POST`；现有 PHP 接口也兼容 `GET` |
| 登录凭证 | 请求头 `token`，使用当前用户的 Live 登录 Token，不是 Go 的 `Authorization` |
| 公共请求头 | 沿用现有 Live 封装生成的签名、时间戳、设备、渠道和版本头；不能只带 `token` 绕过公共验签 |
| 接口语义 | 关注/取关切换；没有通过 `is_followed` 参数指定目标状态的契约 |

完整地址按前端当前 Live 环境拼接，不使用 Go 的 `/go-api` 前缀：

```text
{Live服务域名}{现有Live网关前缀}/api/member/attention
```

没有额外网关前缀时就是 `{Live服务域名}/api/member/attention`；如果 Live 请求封装的 baseURL 已包含 `/api`，相对路径用 `/member/attention`，不要重复 `/api`。实际域名沿用当前项目配置，本文不指定未经部署确认的域名。

**请求参数**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | int | 是 | 被关注主播的 Live 用户 ID，不是房间 ID、社区 uid、HiChat memberId 或 Go 任务 ID |

以下是 JSON 调用示例；Live 通用请求约定也支持表单/query 参数，可沿用现有封装。示例省略的公共签名头仍须由 Live 请求封装补齐。

```http
POST /api/member/attention
token: <当前用户的Live登录Token>
Content-Type: application/json
```

```json
{"id": 520031}
```

`520031` 仅为示例，替换成当前目标主播真实的 Live 用户 ID。

**关注成功响应示例（明文业务数据）**

```json
{"code": 0, "msg": "操作成功", "data": {"id": 520031, "is_followed": 1}}
```

部分 Live 客户端响应只包含加密的 `sec`，需先由现有 Live 网络层解密得到业务数据，再读取 `id`、`is_followed`；不能假设原始响应一定有明文 `data`。

| Live 结果 | 前端后续处理 |
| --- | --- |
| `code = 0`，业务数据为对象，`id` 与本次主播一致且 `is_followed = 1` | 确认本次关注主播成功，再向 Go 申报 `FOLLOW_ANCHOR` 任务 |
| `code = 0`，`is_followed = 0` | 本次是取消关注，不申报任务 |
| `code = 0`，但业务数据为空数组或缺少明确关注结果 | 不申报任务；例如目标是游客时，PHP 可能返回成功及空数组而不执行关注 |
| 非成功码、HTTP 错误、超时或解密失败 | 不直接申报；按现有 Live 错误处理，结果未知时先核对实际关注状态 |

本任务按“关注主播”接入。该 Live 接口也可能对非主播执行社区关注，不能把非主播的社区关注成功当成主播任务完成。切换式接口不能无条件自动重试，否则第一次已经关注成功时，第二次请求可能将其取消。

两次请求的参数不要混淆：**Live 传 `id = 被关注主播的 Live 用户 ID`；Go 传 `taskId = 任务列表中 FOLLOW_ANCHOR 对应任务的 id`。**

## 2. Go 接口地址与登录凭证

| 用途 | 方法 | Go 应用实际路由 |
| --- | --- | --- |
| 获取任务列表 | GET | `/api/points/task/list` |
| 申报任务完成 | POST | `/api/points/task/complete` |
| 查询积分余额、流水 | GET | `/api/points/task/myPoints?pageNum=1&pageSize=20` |

业务描述中的 `/points/task/complete` 是相对路径：**只有请求封装的 baseURL 已包含 `/api` 时，才能直接使用该相对路径。**

例如网关采用 `/go-api` 前缀时，完整地址为：

```text
{Go服务域名}/go-api/api/points/task/complete
```

域名和网关前缀以当前环境为准，不要遗漏或重复 `/api`，不要将任务请求发到 Live 或 Java 服务。

| 请求头 | 要求 |
| --- | --- |
| `Authorization` | Go 任务中心当前账号的完整登录凭证，与任务列表接口一致 |
| `Content-Type` | 申报完成时使用 `application/json` |
| `X-Version` | 沿用真实 App 版本；当前任务列表对这两类任务有 `3.11.6` 及以上的版本展示限制 |
| `Accept-Language` | 沿用客户端当前语言 |
| `X-Request-ID` | 建议携带，便于关联业务成功、任务申报和积分日志 |

Live 请求使用 Live 的凭证；Go 任务请求使用 Go 任务中心的凭证，**不能直接用 Live token 替换**。两次请求必须对应同一实际用户。退出登录或切换账号后，丢弃旧账号尚未处理的业务成功回调。

## 3. 如何取得任务 ID

1. 查询 `GET /api/points/task/list`，确认 Go 响应 `code = 0`。
2. 从响应的 `data` 数组中匹配本次业务对应的 `taskType`。
3. 选择 `taskStatus = 0` 的任务，将该项的 `id` 作为完成接口的 `taskId`。
4. 同类型存在多条符合条件的未完成任务时，逐条申报；已有任务条件仍按列表说明和后端配置执行。

| 业务 | 筛选条件 |
| --- | --- |
| 发帖完成 | `taskType === "DAILY_PUBLISH_SQUARE_POST" && taskStatus === 0` |
| Live 关注成功 | `taskType === "FOLLOW_ANCHOR" && taskStatus === 0` |

- 不硬编码 ID，不按展示名称匹配，不把 `taskCode` 或 `taskType` 当成 `taskId`。
- 发帖任务不是阅读任务 `SQUARE_POST_READ`，也不是评论任务 `SQUARE_POST_REPLY_COMMENT`，不要混用 ID。
- 任务未返回或已完成时不强行申报，可刷新列表确认；不复用其他账号、平台或环境的任务列表。

## 4. 完成接口请求与响应

### 请求

```http
POST /api/points/task/complete
Authorization: <Go任务中心当前账号的完整登录凭证>
Content-Type: application/json
```

```json
{"taskId": 123}
```

`123` 仅为示例，必须替换成任务列表返回的实际 `id`。

- JSON 字段是 `taskId`，不是 `task_id`。
- 只提交任务 ID，不提交会员 ID、被关注者 ID、帖子 ID、积分数量、周期或任务类型。
- 不使用 Java 旧接口的表单传参方式，不额外调用 Java 或 Discuz 加分接口。

### 受理响应

```json
{"code": 0, "msg": "操作成功", "data": null}
```

这是结构示意，`msg` 以实际返回为准；环境开启响应加密时还可能包含 `sec`，不影响读取明文 `data`。

**`code = 0` 只代表申报被受理，不代表任务已落库，也不代表积分已到账。** 后端异步校验任务、保存记录并请求发奖；异步业务拒绝不一定直接体现在这次接口响应中。

Go 登录失效按 `code = -700` 处理，其他错误沿用现有统一错误处理；不要按 Java 的 `code = 200` 判断成功。

## 5. 刷新结果、失败与重试

| 查询接口 | 确认内容 |
| --- | --- |
| `/api/points/task/list` | 对应任务的 `taskStatus = 1`、`finishTime` 有值；`finishTime` 为毫秒时间戳 |
| `/api/points/task/myPoints` | 实际余额 `data.totalPoints` 和流水 `data.pointsRecordPage` |

- 受理后可立即刷新，再按 0.5、1、2、4 秒的间隔有限次数刷新。这是前端建议策略，不是到账时限承诺。
- 达到次数上限仍未完成时显示“处理中/稍后刷新”，保留任务 ID、时间和请求 ID 供排查，不无限轮询或连续重发 `complete`。
- 请求超时、结果未知时先刷新状态；如需重试，使用同一任务 ID 并限制次数，不重新发帖、不重新关注。
- 按当前账号、任务 ID、同一次业务操作对重复点击和重复成功回调去重，防止并发重复申报。
- 主业务已成功时，任务申报失败不能把发帖/关注改显示为失败，也不回滚已成功的操作。
- 不在前端直接增加积分或虚构流水。实际奖励由 Discuz 的规则决定，Go 负责周期防重及发奖失败补偿。

## 6. 上线前确认

| 核对项 | 要求 |
| --- | --- |
| 后端版本 | 当前代码已放开发帖任务，目标环境必须部署包含本次变更的版本；不能仅以 `code = 0` 作为已上线的证据 |
| 任务配置 | 确认任务类型、ID、平台、有效期、积分开关以及 `taskCode` 对应的 Discuz 规则 |
| 原发帖完成回调 | 旧回调继续兼容，代表已经发奖；同周期回调先到则前端不重复发奖，前端先到则回调不重复写记录 |
| 旧发奖来源切换 | 停止同一任务旧的独立发奖来源，只保留必要的历史完成通知；不能仅靠任务记录去重防止两个外部来源同时发奖 |
| 社区积分边界 | 本说明不修改 `post`、`novice_post`、`novice_follow` 规则，不擅自合并、停用或增加这些既有奖励 |
| 关注接法 | 本次选择 Live 关注成功后申报；不同时走 Go 关注业务自动触发链路 |

本次仅修改 Go 发帖任务限制并补充回归测试，未改 Java/PHP、未改数据库表结构、未请求真实积分、未执行部署。Go 不新增帖子证据校验，发帖是否完成由前端按业务成功回调判断。

## 7. 前端联调验收清单

- [ ] 发帖完成后提交正确发帖任务 ID，任务完成且真实奖励符合配置。
- [ ] Live 关注成功后提交正确关注任务 ID，未额外调用 Go/Java 关注接口。
- [ ] 发帖失败、保存草稿、关注失败、取消关注均不申报。
- [ ] 重复点击、重复回调不并发重复申报，同周期奖励不重复。
- [ ] 登录失效或切换账号后，不使用旧账号的业务回调或任务 ID 申报。
- [ ] 异步拒绝或发奖失败时，不虚报完成或到账，不影响主业务成功展示。
- [ ] 发帖待审核口径、旧发奖来源切换、目标环境后端版本均已确认。
