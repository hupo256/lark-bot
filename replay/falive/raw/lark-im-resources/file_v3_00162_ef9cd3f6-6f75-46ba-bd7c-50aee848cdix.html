三个入口只在「怎样确定助理」这一步不同，之后都进入同一个 LChatAnchor::sendMessageVoid。同步阶段只写 Redis 并推送；房间、成员、消息由定时器从队列批量写进 MySQL。

房间 vid 怎么来
vid = Hashids(salt="pmvid", 长度 32, 字母表 A–Z0–9).encode(助理 id, 用户 id)

同一对（助理, 用户）永远得到同一个 vid，不查库就能算出；反解后第 1 位是助理，第 2 位是前台用户。旧版十六进制 vid 反解不出来，只能查 cmf_chat_room_user。实现见 LCreatePmVid。

绑定怎么维持

  • Key：table/user/getAvailableOne:0-{uid}（前台）。后台「会员分配」用 1-{uid}，两者互不覆盖。
  • 有效期：按请求所属平台读 invite_sys_time（小时，默认 8）。每次命中都续期，所以用户持续聊天就一直是同一个助理。
  • 写入时机：级联抽到人且 anchorId > 0；帮助中心每次重抽都写。anchorHistory 在未绑定、也没配公共欢迎语时会顺手分配并写绑定，也就是说用户只是打开私聊窗口就绑上了。
  • 视为无效：绑定的是超管，或已 canChat = false。这时不删 key，重抽后覆盖。
  • 不检查：助理是否在线、是否仍是当前主播的助手、是否同平台。用户换到另一个主播的直播间私聊，仍会连到原来的助理。
  • 另一套读法：anchorHistory 用 APmRoom::checkAssign 直接读 key，不做上面的有效性判断；旧发言路径 setAvailableOneMoreTime 会把有效期改回固定 8 小时。

发言时序 sendMessageVoid → sendAnchorMessage

一条消息从进入发言核心到返回的实际执行顺序。注意文本校验在第 7 步才做：超长或空消息被拒之前，房间已经登记、欢迎语也已写入。

  1. 冻结检查。Redis 有 chat_freeze:{uid} 就抛 You are freeze。
  2. 算 vid。LCreatePmVid::encode(助理, 用户)。
  3. 防重复。seed 非空、且本机 APCu 已有这条 seed 的记录（保留 999 秒）时，直接返回上次结果。
  4. 判断是否首条。Redis 里 hst:{vid} 不存在就算首条。3 天无消息后 key 过期，再发一条也算首条。
  5. 登记房间。APmRoom::insOrUpdCache：校验 vid 与助理是管理员 → 前台会话列表 hSetNx → inviteroom:{助理} 300 秒 → 推入 pm-room-db-queue。
  6. 首条先写欢迎语（规则见下一节）。
  7. 发送 sendAnchorMessage
    • 文本：最多 801 字，连续空白压成一个，去掉换行；非图片消息不能为空；按房间平台做敏感字替换和敏感字换图。
    • 图片：msgType 2 / 3 由服务端接收上传文件并生成 bnc；4 / 5 / 6 直接用前端传的路径（去掉域名）。
    • 组包：action=send、qos=1、cross_userid=[助理, 用户]、anchor_id、pm_source_type，pm_source_type_str 写助理 id。
    • 写 Redis 历史并推入消息入库队列 msg_to_db:，同时更新最后一条消息。
    • 推送前把手机号打码；Redis 历史里保留原文。
    • UMsg::send 推给助理和发送者本人，出口处补 platform_id。
    • 后台红点、newRoom 通知、后台私聊列表 roompmvid:2:{助理}（7 天，最多 2000 个房），前台会话列表更新入队。
  8. 主播私聊首条：补一条助理欢迎语，作为响应里的 msg 返回给前端。
  9. 记录 seed，供第 3 步去重。
  10. 注册用户：LChatSystemBindXing::replyBindAfter。如果这个房间正处在杏彩 / 邮箱绑定流程，就把这条文本当作账号去绑定。

助理回复时的闸门

后台发言（LWebChat::sendMessage，isFront = false）依次检查：

  1. 管理员 canChat 为 false → NO_PLATFORM_PERMISSION。
  2. 取房间平台（缓存里是 0 就回源再查一次），仍为 0 → DIFFERENT_PLATFORM_ROOM。房间平台在建房时写入，取的是前台用户的平台：注册用户看 registration_id，游客看渠道。
  3. 房间平台属于该管理员的平台 → 放行。
  4. 否则，管理员已在 cmf_chat_room_user 里 → 放行（给「分到了其他平台的助理」兜底）；不在 → DIFFERENT_PLATFORM_ROOM。
  5. vid 反解后第 1 位必须是发言的管理员本人，否则 You are not in room。

欢迎语 app/caching/chat/AWelcomeMessage.php

  • 按哪个平台取：先用前台用户自己的平台（getPlatformIdByUser），取不到再用房间平台。
  • 公共发送者：平台配置 welcome_sys_uid，按平台取，不回落全站。
  • 内容：一条配置里有 text1–3，从非空的几条里随机取一条。
  • 发送者资料：AUser 基础资料，再用助理在该平台的昵称、头像覆盖（BUG-4792）。
  • 存储：只写 Redis 历史，不入库；后台看历史时跳过 welcome = 1 的消息。

已知偏差

代码行为和规则（或注释、注解）不一致的地方，按影响排序。

  1. 高
    私聊历史可越权读取

    history、getChatHistory、read 不校验 vid 是否属于当前用户，room_type 传 0 也能读。vid 可以由（助理 id, 用户 id）推算，于是能读到别人和助理的完整对话；旧接口遇到空房还会往别人的房里写一条欢迎语。

    LApiChat.php:34 · LBaseChat.php:153 · CChat.php:350
  2. 中
    指名私聊没有平台和可收发校验

    可以私聊超管、没有助手组的管理员、其他平台的助理；其他平台的助理还能回复（「已在房内」豁免）。注解上写着会检查，代码里没有。

    LChatAnchor.php:443 · CChat.php:1149 · LWebChat.php:621
  3. 中
    新房间的平台暂时是 0

    入库是异步的，发送时查房间平台得到 0，并在本机缓存最长 30 秒。结果是新房前几条消息的敏感字、主播私聊的第二条欢迎语都没有按用户平台处理。

    LChatAnchor.php:173 · LChatAnchor.php:504
  4. 中
    来源字段记错

    sendToAnchor 的来源固定是 0；pm_source_type_str 一律写助理 id；杏彩求助记成 1（直播间私聊）。后台「用户来源」会把助理自己的昵称显示成来源。

    CChat.php:969 · LChatAnchor.php:228 · LUserXingHelp.php:43
  5. 低
    绑定的有效性判断不一致

    注释要求「在线且仍是当前主播的助手」，代码只看 canChat；anchorHistory 完全不判断有效性；anchorId = 0 时不写绑定，每条消息都可能分给不同助理；旧路径把有效期改回固定 8 小时。

    AUserAssignAnchorAssistant.php:164 · :190 · :229 · :369
  6. 低
    帮助中心分配不看在线状态、不剔除超管

    离线助理也会被分到；而且每次请求都直接查库，没有缓存。

    AUserAssignAnchorAssistant.php:272 · :297
  7. 低
    T3 与 T1 是同一个查询

    渠道参数只进了缓存 key，没有参与计算，第三档永远查不出新结果。

    AAssign.php:34 · AUserAssignAnchorAssistant.php:74
  8. 低
    其他

    助理和公共发送者都没配欢迎语时，前台会收到文本 "1"；私聊没有发言频率限制；seed 去重只在本机 APCu 生效，重试落到另一台机器时会重复发送。
