## 逐条说明

### 1. C5 热门主播 → 他人主页

**回复：已修复，待发布到 pre。社区接口的用户 ID 统一改成 live 用户 ID，前端需要适配。**

- 社区（bbsv2）接口收到和返回的用户 ID 一律是 **live 用户 ID**，跟直播接口是同一个值。社区 uid 只在服务端内部换算，不再出现在接口里（只有心跳里的 `community.dz_uid` 保留，仅供排查）。
- 热门主播进他人主页：直接用主播的 live 用户 ID 调 `member/otherInfo?uid=<live 用户 ID>`。他人主页后续的帖子列表（`thread/listCursor?uid=`）、帖子数（`member/threadsCount?uid=`）、关注（`member/follow`）都用同一个 ID，不用再换。
- 主播还没开通社区账号时，服务端当场替对方开通，照常返回资料：昵称、头像、直播等级、开播状态；社区侧的帖子数、积分等为 0。
- 对方不是主播、也没进过社区时，只返回直播侧基础资料，社区字段为默认空值，`uid` 照常是传入的 live 用户 ID；这时在社区里关注 TA，服务端会替对方开通社区账号。
- 直播侧查无此人（含游客 id）时报「用户不存在」。
- 返回里所有用户 ID 也都是 live 用户 ID：帖子 / 评论 / 搜索结果的 `authorid` 和 `author.uid`、通知触发者、推荐作者、相关作者、搜索作者、关注 / 粉丝列表、`member/info` 和 `member/otherInfo` 的 `uid`。关注列表里纯直播端的关注以前 `uid` 是 0，现在也有值。
- **作者没有 live 用户时 `uid` / `authorid` 为 `0`，头像、昵称做成不可点。** 这类作者是嗨聊开的社区号还没对应到 live 用户；上线前服务端会跑全量迁移补齐，剩下的只有极少数补不了的老号。
- 今天早些时候给 `member/otherInfo` 加的 `live_uid` 参数和响应字段已经撤掉，以本条为准。
- 前端改动：
  - 他人主页入口一律传 live 用户 ID，不再显示「暂未开放」。
  - 已经按社区 uid 写的地方改为直接用返回的 `uid`。
  - 判断「是不是我自己」直接拿 `author.uid` 跟当前登录用户 ID 比。
  - `uid=0` 时头像不可点。
- 接口说明见 `doc/bbsv2/PM-2954-App对接文档.md` 顶部 2026-10-19 那条和各接口说明。

### 3. C2 话题 chip 顺序

**回复：暂不改，目前按照热度排序。**

- `forum/hotTags` 的排序规则：按标签在当前平台被帖子使用的次数从高到低排（只统计正常显示的帖子）；次数相同时，新建的标签排在前面。
- 当前平台还没有任何帖子带标签时，按标签字典的创建先后排序。
- 结果有约 2 分钟缓存，新帖打上标签后，顺序最多晚 2 分钟变化。
- 标签表目前没有运营排序字段。要固定顺序，后端需要加排序字段、后台需要加编辑入口，等产品确认要做再排期。前端不用等这一项，按接口返回的顺序展示即可。

### 10. LN10 `member/attention` 返回结构

**结论：接口实际返回的就是扁平结构，前端按扁平解析是对的，接口不用改。前端看到的「嵌套」出自 /doc 自动生成的接口页面，是后端接口注释的写法问题。**

**接口实际返回**（`GET|POST /api/member/attention`，参数 `id` 为对方 live 用户 ID；切换式：已关注就取消，未关注就关注）：

```json
{ "msg": "操作成功", "code": 0, "data": { "id": 520031, "is_followed": 1 } }
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `data.id` | int | 对方用户 ID，原样返回请求里的 `id` |
| `data.is_followed` | int | 操作之后的状态：1 已关注 / 0 已取消 |

**/doc 页面显示的示例**：

```json
{ "code": 0, "msg": "成功信息", "data": { "data": { "id": 12345, "is_followed": 23456 } } }
```

返回字段表也列成了 `data.id`、`data.is_followed`。

**原因**：

- /doc 页面按接口注释生成返回示例。注释里的字段路径应当相对 `data` 来写（例如 banner 接口写 `[].id`），生成示例时再整体放进响应的 `data` 里。
- `member/attention` 的注释写成了 `data.id`、`data.is_followed`，多带了一个 `data.` 前缀，所以示例被套成了 `data.data.id`。
- 另外，/doc 示例里 int 字段填的是随机数，`is_followed` 显示成 0 / 1 以外的值，不代表真实取值。

**以哪份文档为准**：对接文档 `doc/live/live-接口与业务说明/01-用户与账号.md` 第 1.39 节写的是扁平结构，和实际返回一致，以它为准。

**边界情况**（前端解析时注意）：

- 对方 id 是游客 id 时，返回成功，但 `data` 是空数组 `[]`，没有 `id` / `is_followed`。
- 当前用户是游客：报错 `You are not a member and cannot use this feature`。
- 关注自己：报错 `Can not focus on yourself`；`id` 没传或为 0：报错 `Parameter error`。

**后端处理**：把注释里的 `data.id` / `data.is_followed` 改成 `id` / `is_followed`，/doc 示例就会恢复成扁平结构。接口返回不变，前端不用改。

社区关注列表里 `follow_type` 为 `live` / `both` 的人，取关就调这个接口，见第 11 条。

### 11. 关注列表取关调哪个接口（补充）

**回复：已新增，待发布到 pre。两个关注接口都没改，前端按新字段选接口，一次就能调对。**

- `member/friendsCursor` 的列表项新增 `follow_type`（string），表示我对 TA 的关注在社区、直播哪一边：

| 值 | 含义 | 取关调哪个接口 |
|---|---|---|
| `community` | 只在社区关注 | `POST /bbsv2/member/follow`，`uid` 传列表项的 `uid`，`action=0` |
| `live` | 只在直播端关注 | `/api/member/attention`，`id` 传列表项的 `uid`（切换式，返回 `is_followed=0` 即已取关） |
| `both` | 两边都关注 | 上面两个都调 |
| `none` | 此刻两边都没关注 | 不用调，按「未关注」展示 |

- 按请求当下两边的关注记录算。`type=follow` 列表本身最长 10 分钟才刷新，刚在直播端取关的人还会列着，这时 `follow_type=none`、`is_follow=0`。
  不看这个字段直接调 `/api/member/attention` 的话，因为它是切换式，会把已经取关的人又关注回去。
- `type=fan`（粉丝列表）只看社区侧：回关了为 `community`，没回关为 `none`（只在直播端关注了这个粉丝的也是 `none`）；回关调 `member/follow` `action=1`。
- 以前要先调 `member/follow`，报 `BBSV2_FOLLOW_MISSING` / `BBSV2_USER_NOT_EXIST` 再换直播接口，现在不用试错。
- 接口说明见 `doc/bbsv2/PM-2954-App对接文档.md` 的 `member/friendsCursor`（顶部 2026-10-19 也有一条）。
