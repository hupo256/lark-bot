## 0. 一句话概览

- 模块路径：`app/http/bbsv2/`，路由固定为 `/bbsv2/{controller}/{action}`（自动路由，小写控制器名去掉 `C` 前缀，如
  `CThread::detail` → `/bbsv2/thread/detail`）。
- 10 个控制器：`CIndex`（首页/健康检查）、`CForum`（版块/标签）、`CThread`（帖子）、`CPost`（评论）、
  `CSearch`（搜索）、`CMember`（会员中心）、`CFavorite`（收藏）、`CTool`（上传）、`CNotify`（站内通知）、
  `CPreload`（预加载，见 2.10）。
- 鉴权：复用现有 App 登录态，请求头带 `Token`；未登录也能访问的接口标了「公开」，其余标「需登录」。
- 平台隔离：由服务端根据登录态 / 渠道号自动识别，**App 不需要传也不需要关心 platform_id**——服务端内部按
  平台隔离数据，但接口响应里不会带 `platform_id` 字段。
- 响应包体、加密（`sec`）、错误码规则跟现有直播 App 接口完全一致，App 侧现有的解密/错误处理逻辑可以直接复用，
  见第 1 节。
- 多数分页列表提供两种加载方式：`page`/`per_page` 翻页；游标翻页（`xxxCursor` + `last_id`，配合
  `xxxNewCount` + `since_id` 做下拉刷新新内容提示），用于"信息流往下滑加载更多"场景，避免翻页漂移，
  见 1.5。**帖子列表（`thread/listCursor`）与好友/粉丝列表（`member/friendsCursor`）只提供游标版本**。

## 1. 通用约定

### 1.1 鉴权与平台识别

- 登录态：跟现有 App 接口一致，请求头 `Token: <token>`。标了「需登录」的接口未带 Token（或 Token 失效）时，
  返回业务错误码 `-700`，`msg` 为 `Login status invalid, no TOKEN`，App 侧应统一按"未登录/登录失效"处理
  （跳登录或刷新 Token）。
- 平台识别：登录态下取用户注册渠道对应的平台；未登录（游客）时取请求渠道号（跟现有 App 请求头/参数一致，
  不需要额外接入）。识别不到时兜底为平台 1。**App 不需要也不应该自己传 platform_id，接口响应里也不会
  带这个字段**，只需要保证登录 Token / 渠道号跟现有接口一样正常带上即可。
- 版块（forum）、帖子（thread）都归属某个 `platformid`；前台只认当前平台的圈子（Discuz 群组：`type=sub`、`status=3`、
  `level>=0`，跟嗨聊同一批圈子，普通版块不用），其它版块及其帖子、不属于当前平台的版块/帖子，前台接口一律当作不存在
  （`BBSV2_FORUM_NOT_EXIST` / `BBSV2_THREAD_NOT_EXIST`），不会跨平台泄漏。

### 1.2 请求方式

**请求方式按第 2 节每个接口标注的严格校验（2026-10-03 起，所有环境）**，用错直接拒绝：

- 只读查询（list / detail / hotTags / thread / author / combo 等）：**只接受 GET**（HEAD 按 GET 处理）。
- 会产生写入的动作（`favorite/add` `favorite/remove` `member/follow` `notify/markRead` `notify/markAllRead`
  `post/create` `post/recommend` `thread/create` `thread/recommend` `tool/upload`，共 10 个）：**只接受 POST**。
- 方法不对 → **HTTP 405**，响应头 `Allow` 给出允许的方法，包体仍是标准 JSON 错误结构：`code=-1`、
  `msg` 为 `BBSV2_HTTP_METHOD_NOT_ALLOWED`（「请求方式错误，请使用 POST」）。
- POST 用 `Content-Type: application/json` 传参时，请求体必须是合法 JSON；解析失败 → **HTTP 400**，`code=-1`、
  `msg` 为 `BBSV2_REQUEST_BODY_INVALID`（「请求数据格式错误」），接口不会执行（原先会当成空参数照常执行）。
  `application/x-www-form-urlencoded` / `multipart/form-data` 不受影响。
- `tool/upload` 必须 `multipart/form-data`，文件字段名固定为 `file`。
- 形参为数组的（如 `images`、`tags`），可以传数组，也可以传西文逗号分隔的字符串（框架自动转数组），
  App 用 `?images=12,13&tags=1,3,5` 或标准数组编码都可以。
- **参数错误 → HTTP 418**（2026-10-09 起，所有接口）：第 2 节标为必填的参数没传或传空串、数字参数（`tid` / `pid` /
  `uid` / `page` 等）传了非数字串（如 `tid=abc`、`uid=room-2`）、单值参数传了数组（如 `tid[]=1`），接口不会执行，
  直接回 **HTTP 418**。包体是**明文** JSON（不走 `sec` 加密）：`code=-1`、`data=[]`，`msg` 是给开发排查用的中文说明
  （含接口名与出错的参数名，**未翻译**），不要直接展示给用户。418 只会是客户端传参问题，请按「请求参数有误」统一处理并修正传参。

  ```json
  { "code": -1, "data": [], "msg": "app\\http\\bbsv2\\ctrl\\CThread::detail 参数 类型错误(应为数字), 请客户端协调检查：tid - ExceptionCode:0" }
  ```

### 1.3 响应包体

跟现有直播 App 接口完全一致的标准包体：

```json
{
  "code": 0,
  "msg": "Operation successful",
  "data": { ... },
  "sec": "<base64 加密串>"
}
```

- `code`：`0` = 成功；非 `0` = 失败（bbsv2 目前业务错误统一返回 `-1`，两个特例：「未登录」固定 `-700`；
  `thread/detail` / `preload/threadDetail` 的「帖子不存在」固定 `-3`，客户端据此直接落"帖子不存在"页。
  其余错误类型请看 `msg` 对应的 lang key，见第 3 节错误码表）。业务错误的 HTTP 状态码都是 200；
  非 200 的只有 1.2 里的三种请求层错误：方法不对 405、JSON 请求体解析失败 400、参数错误 418。
- `msg`：提示文案（已按当前语言环境翻译）。
- `data`：**生产环境下大多数场景不会出现这个字段**，只有登录态处于加密白名单（debug/内网调试等）时才会带
  明文 `data`。正式环境请求返回的是加密字段 `sec`。
- `sec`：`data` 明文 JSON 先 `gzcompress` 再 AES-128-ECB 加密后 base64 得到，跟现有直播 App 接口的加密方案
  完全一样（同一套 key/算法），App 现有的解密工具函数直接复用即可，本文档不重复列出 key。
- 分页接口在最外层多一个 `page` 字段（见 1.4）。

调试期如需直接看明文 `data`，可以：

- 用后端提供的联调环境（`app()->isDebug()` 为真）；或
- 让服务端把你的调试域名/IP 加进 `APP_RESP_DATA_SKIP_SIGN_*` 白名单。

线上正式环境所有 App 真实请求都必须走 `sec` 解密，不要假设 `data` 一定存在；唯一例外是 2.10 的
`preload/*` 预加载接口（免验签，直接返回明文 `data`）。

### 1.4 分页结构

分页接口响应最外层多一个 `page` 对象：

```json
{
  "code": 0,
  "data": { "list": [ ... ] },
  "page": {
    "hasNextPage": true,
    "nowPage": 1,
    "pageSize": 10,
    "allCount": 42,
    "extData": []
  }
}
```

分页型接口的请求参数固定为 `page`（从 1 开始）+ `per_page`（每页条数，服务端会 clamp 到 `[1, 50]`，超过
50 按 50 算）。

### 1.5 游标翻页

`page` 分页在"信息流往下滑加载更多"场景下有漂移问题：翻页过程中如果列表头部插入了新内容
（新帖子/新评论/新收藏……），后面几页会漏取或重取。游标翻页用于解决这个问题，App 按场景选：

- **列表页/详情页首次加载、支持跳页、按热度/浏览量等自定义排序**：用 `page`/`per_page`（见 1.4）
  ——适用于 `post/list` `search/thread` `member/credit` `member/threads` `favorite/list`。
- **"往下滑自动加载更多"的信息流场景**：用同一资源下的 `xxxCursor` 接口（`thread/listCursor`
  `post/listCursor` `search/threadCursor` `member/creditCursor` `member/friendsCursor`
  `member/threadsCursor` `favorite/listCursor` `index/recommendAuthorsCursor`），用 `last_id`
  （`index/recommendAuthorsCursor` 是 `last_cursor`）代替 `page` 翻页。

> ⚠️ 两个资源**只提供游标版本，没有 `page` 分页接口**：
> - 好友/粉丝列表：只有 `member/friendsCursor`，见 2.6。
> - 帖子列表：只有 `thread/listCursor`，固定按时间序（`tid desc`），不支持自定义排序与跳页，见 2.3；
>   需要热门帖子时用 `thread/hot`（热门榜，非分页一次性返回；按热度指标挑帖，返回顺序同样是发布时间倒序——
>   bbsv2 所有帖子列表统一时间倒序，没有任何接口按热度排列）。

**用法**：不传 `last_id`（或传 0）= 第一页；把上一页拿到的 `next_cursor` 原样传给下一次请求的
`last_id`，直到 `next_cursor` 回传 `0` 为止（没有更多了）。`per_page` 语义跟 `page` 模式一样。

```text
GET .../bbsv2/thread/listCursor?per_page=10          -> 第一页
GET .../bbsv2/thread/listCursor?last_id=1000811&per_page=10   -> 下一页
```

响应结构跟 `page` 模式不同：**没有最外层 `page` 字段**，`data` 里多一个 `next_cursor`：

```json
{ "code": 0, "data": { "list": [ ... ], "next_cursor": 1000805 } }
```

⚠️ **约束**：游标接口排序固定为对应资源的"默认时间序"（帖子/搜索/收藏/积分记录按创建顺序倒序，
评论区按楼层顺序正序，好友/粉丝按关注时间倒序），**不支持** `order`/`sort`/`orderby` 等自定义排序
参数——`search/thread` 按最后回复/浏览/回复数排序用它的 `page` 模式（见 2.5）；帖子列表按热度/浏览量
排序用非分页的 `thread/hot`（见 2.3）。好友/粉丝游标翻页的 `last_id` 语义是"上一条的关系建立时间戳"而不是用户 ID（关系表没有自增 ID），
同一秒内建立的多条关系在翻页边界上理论上有极小概率漏取/重取，量级上可忽略。

**配套的"新内容计数"接口**（`thread/listNewCount` `post/listNewCount` `search/threadNewCount`
`member/creditNewCount` `member/friendsNewCount` `member/threadsNewCount` `favorite/listNewCount`
`notify/listNewCount`）：下拉刷新时，把当前信息流最上面一条的 id（`since_id`）传过去，只返回一个数字，
不返回数据：

```json
{ "code": 0, "data": { "count": 3 } }
```

用于"下拉刷新时提示『有 3 条新内容，点击查看』"，count>0 时 App 可以选择直接调用对应的
`page`（`page=1`）或 `xxxCursor`（不传 `last_id`）接口重新拉取顶部内容替换展示。

每个资源具体的字段/参数见第 2 节对应小节的"游标翻页"/"新内容计数"条目。

### 1.6 内容类型（media_type / mediatype）

帖子按有没有视频/图片自动判定内容类型，落库字段 `mediatype`，取值：

| 值 | 含义 |
|---|---|
| 1 | 纯文字 |
| 2 | 图片（无视频，有图片） |
| 3 | 视频（只要带视频就是这个，跟是否同时有图片无关） |

`thread/listCursor` 的 `media_type` 筛选参数用同一套取值，`0` = 不筛选。

> 嗨聊 App 发的帖子：接口返回的 `mediatype` 按正文里实际的图片 / 视频给（2026-11-01 起发的），一发出来就是对的；
> `media_type` 筛选按库里的值，新版嗨聊发帖时会写入，老版本嗨聊发的帖是 `1`，筛「图片」「视频」时筛不出来。

### 1.7 标签（Tag）使用流程

发帖标签**不支持自由输入新词**，只能从后台维护的标签字典里选：

1. 先调 `forum/hotTags`（不传 `keyword` = 热门标签云；传 `keyword` = 按名搜索已有标签）拿到
   `[{tagid, name, count}, ...]`；如果标签选择器要给一个"查看全部标签"的入口（不局限于热门 Top N），
   改调 `forum/allTags`，拿到字典全量 `[{tagid, name}, ...]`（没有 `count`）。
2. 发帖 `thread/create` 的 `tags` 参数传选中的 `tagid` 数组，最多 5 个，必须是字典里已存在的
   tagid，否则报 `BBSV2_TAGS_INVALID`。
3. 帖子详情/列表里的 `tags` 字段是标签名字符串数组（`string[]`），展示用，不是 tagid。

### 1.8 图片/视频上传流程（发帖/回帖带图带视频）

1. 每个文件先单独调 `tool/upload`（需登录，`multipart/form-data`，字段名 `file`），拿到返回的 `aid`。
   - 图片：`image/jpeg` `image/png` `image/gif` `image/webp`，单文件 ≤ 10MB。
   - 视频：`video/mp4` `video/quicktime` `video/x-msvideo` `video/x-matroska`，单文件 ≤ 50MB
     （视频时长在这一步就会返回，`duration` 单位毫秒）。
   - 超过大小上限报 `BBSV2_UPLOAD_SIZE_LIMIT`（「文件不能超过 10MB / 50MB」，`msg` 里带具体上限，2026-10-03 起；
     原先只回笼统的 `BBSV2_UPLOAD_FAILED`）。注意请求体再大到超过网关上限时会被网关直接拦下，返回网关自己的
     HTTP 413 页面（不是 JSON），建议 App 上传前本地先按上面的上限校验文件大小。
   - **类型按文件内容判定**：multipart 里声明的 Content-Type 只决定按图片还是按视频探测，真实类型由服务端
     按文件内容识别（图片看图片头，视频看容器头）。内容不是上面列出的类型（如把文本/可执行文件改名或改
     Content-Type 伪装成图片）报 `BBSV2_UPLOAD_TYPE_INVALID`；零字节文件报 `BBSV2_UPLOAD_FAILED` 或
     `BBSV2_UPLOAD_NO_FILE`（不再是 HTTP 500）。落盘扩展名按真实类型生成，不取客户端文件名的后缀，
     返回的 `url` 后缀可能与上传时的文件名不同，App 侧不要依赖 `url` 后缀等于原文件名后缀。
   - **防重复提交**：同一登录用户 60 秒内用相同的「文件名 + 文件内容」重复调 `tool/upload`（典型场景是
     弱网重试/按钮双击），服务端会直接原样返回上一次的结果（同一个 `aid`），不会新建附件记录——App 侧
     不需要自己做防抖，正常重试即可；超过 60 秒或文件名/内容任一变化则视为新文件正常上传。
     同一份文件**同时**发起多个上传请求时，只有先到者真正上传，其余请求等它传完、拿到同一个 `aid`
     （最多等 15 秒；先到者失败则由下一个请求重传）——并发 200 次也只产生 1 个附件（2026-10-03 修复：原先
     偶发产生 2 个）。
   - **图片压缩 + 缩略图（服务端自动）**：非 GIF 图片上传后服务端会按 EXIF 方向转正并去掉 EXIF（含 GPS），
     长边大于 1920 的等比缩到 1920，再转 webp（质量 80，PNG 透明保留）与原图比大小，更小才存 webp，否则保留
     原格式（长边超 1920 仍存缩放版）；原图 ≤ 100KB 且长边未超限的原样保存。返回的 `url` 是处理后的主图，
     后缀可能变成 `.webp`。同时生成一张宽 ≤ 400 的 webp 缩略图，地址在返回的 `thumb` 里，发帖前预览可直接用。
     GIF 原样保存、不压缩、不出缩略图（`thumb` 为空字符串）。10MB 上限限制的是上传进来的原文件；另有总像素
     上限 5000 万（宽×高），超过报 `BBSV2_UPLOAD_PIXEL_LIMIT`。视频封面帧同样会出缩略图。
   - **落盘加密**：图片（主图 + 缩略图，含 GIF）与视频封面帧（+ 缩略图）存到服务器上是密文，`url` / `thumb`
     直接贴进浏览器看不到图，App 显示前要先解密，见 1.10。视频文件本身不加密。
2. 发帖 `thread/create`：`images` 传图片 aid 数组（顺序即展示顺序，**最多 5 张**，超过报
   `BBSV2_IMAGES_TOO_MANY`「最多只能上传 5 张图片」；上限也可从 `thread/publishRule` 的 `max_images` 取），
   `video` 传视频 aid（`0` = 无视频，一个帖子只能有 1 个视频）；`content` 是纯文本正文（换行用 `\n`，不要传 HTML/BBCode；
   不含图片/视频，服务端会按 `images`/`video` 自动拼装）。
3. 回帖 `post/create` **不支持带图片/视频**（只有 `message`）；`message` 里带 `<img>` 或附件标记会报
   `BBSV2_REPLY_ATTACH_UNSUPPORTED`——UI 上不要给
   回帖框加图片/视频入口。

### 1.9 发帖/评论正文长度与频率限制（发帖规则）

`thread/create`（正文，允许纯图片/视频时为空）与 `post/create`（回复 `message`）在内容合法性校验之后，
还会再过一遍后台「全局 -> 发帖设置」配置的规则（`minpostsize`/`maxpostsize`/`floodctrl`，值为 `0`
表示后台未启用该项，不做限制，**具体阈值以后台当前配置为准，App 不要写死假设值**）：

- **字数下限/上限**：正文（`trim` 后按字符数计）短于 `minpostsize` 或长于 `maxpostsize` 时拒绝发布，
  分别报 `BBSV2_CONTENT_TOO_SHORT` / `BBSV2_CONTENT_TOO_LONG`（`msg` 里的 `{:size}` 已替换成具体阈值）。
  帖子允许纯图片/视频（`content` 传空串）时跳过这项检查。
- **发帖间隔（冷却期）**：同一用户两次发布（发帖或回复，**共用同一把冷却锁，不分动作类型**）间隔小于
  `floodctrl` 秒时拒绝，报 `BBSV2_POST_TOO_FREQUENT`（`msg` 里的 `{:seconds}` 是配置的冷却秒数）。
  UI 上建议在发布按钮点击后先本地防抖，命中此错误码时提示"发帖太频繁，请稍后再试"。
- **重复提交（2026-10-03 起，恒启用，不受后台配置影响）**：同一用户 60 秒内在同一场景再次提交**相同内容**时拒绝，
  报 `BBSV2_DUPLICATE_SUBMIT`（"请勿重复提交相同的内容"）。用来挡连点发布按钮、网络超时后自动重发造成的重复帖子 / 评论；
  正常连续发不同内容不受影响。判定口径：
  - 发帖：标题 + 正文（首尾空白不计）+ 图片 + 视频 + 标签都相同；
  - 评论：同一主题、同一回复对象（`pid`）+ 正文（首尾空白不计）相同；同样的文字回复另一条评论不算重复；
  - 发帖与评论各自判重，互不影响；只跟本场景**上一次**提交比对；
  - 提交被拒（违禁词、附件无效、评论对象不存在、发帖太频繁等）不算一次提交，修正后可以马上重试。

  App 收到这个错误码时，可以当作"上一次已经提交成功"处理（刷新列表即可看到），不要再弹失败重试。

**标题/内容长度上下限本身可以在提交前查到**：调 `GET /bbsv2/thread/publishRule`（公开，见 2.3），拿到
标题、内容各自的 `{min, max}`，用于输入框实时显示剩余字数/超限提示，不用等提交报错才知道限制。
标题上限固定 80、下限固定 1（不随后台配置变化）；内容上下限就是本节的 `minpostsize`/`maxpostsize`，
`max`/`min` 为 `0` 时表示该项未启用，App 应按"不限制"展示，不要当成"最多 0 字"。这个接口**不含**
发帖间隔（`floodctrl`）——间隔是运行时冷却状态，不是可提前查询的静态字段限制，仍只能靠提交后命中
`BBSV2_POST_TOO_FREQUENT` 处理。

### 1.10 图片加密：客户端按文件头解密

部分图片在服务器上是**密文**，地址直接贴进浏览器只会下载到一堆二进制。所有显示图片的地方——`picture[]`、
`video[].cover`、`tool/upload` 返回的 `url` / `thumb`——都要走同一套处理：

1. 取回图片的字节；
2. 看开头 7 个字节：是 ASCII `HCIMG1` 加一个字节 `0x01` 就是密文，按下面解密后用**解出来的字节**显示；
3. 不是就是明文，原样显示。

**接口不会告诉你哪张是密文，一律按文件头判断。** 同一个列表里密文、明文会混着出现：bbsv2 上传的图片（含缩略图、
视频封面）、嗨聊网页发帖的附件图是密文；嗨聊 App 发帖正文里的图、审核打码图、头像、默认图等是明文。视频文件不加密。

**格式**（与嗨聊社区 PM-2783 完全一致，嗨聊新版 App 的 `X-Image-Mode: encrypted` 也是这套）：

| 字节 | 内容 |
|---|---|
| `[0, 6)` | magic，ASCII `HCIMG1` |
| `[6, 7)` | 版本，恒为 `0x01` |
| `[7, 19)` | IV，12 字节 |
| `[19, 35)` | GCM 认证标签（tag），16 字节 |
| `[35, 结尾)` | 密文 |

**算法**：AES-256-GCM，tag 128 位，没有附加数据（AAD）。密钥（64 位十六进制，即 32 字节）：

```text
f636b71205fe98a1e2d9f8973cfeb888716566e943581cfcbbd41299eb2c5b8a
```

解出来的就是原图字节（jpg / png / webp / gif），直接交给图片控件解码。

**参考写法**：

**Web / H5 / PC（React）**：三端共用下面这个模块（TypeScript；JS 项目去掉类型注解即可），浏览器自带 WebCrypto，不用装依赖。

```ts
// hcImage.ts
const KEY_HEX = 'f636b71205fe98a1e2d9f8973cfeb888716566e943581cfcbbd41299eb2c5b8a';
const MAGIC = [0x48, 0x43, 0x49, 0x4d, 0x47, 0x31]; // 'HCIMG1'
const MAX_CACHE = 200;                               // 最多缓存多少张解密后的图，超出淘汰最久没用的

let keyPromise: Promise<CryptoKey> | null = null;
function getKey(): Promise<CryptoKey> {
  if (!keyPromise) {
    const raw = new Uint8Array(KEY_HEX.match(/../g)!.map((h) => parseInt(h, 16)));
    keyPromise = crypto.subtle.importKey('raw', raw, 'AES-GCM', false, ['decrypt']);
  }
  return keyPromise;
}

/** 下载到的字节 → 原图字节：明文原样返回，密文解密；解不开（损坏 / 被改）抛错 */
export async function decodeImage(ab: ArrayBuffer): Promise<ArrayBuffer> {
  const buf = new Uint8Array(ab);
  const isEnc = buf.length >= 35 && MAGIC.every((b, i) => buf[i] === b) && buf[6] === 1;
  if (!isEnc) return ab;

  // WebCrypto 要求 tag 接在密文后面：[35, 结尾) 的密文 + [19, 35) 的 tag
  const joined = new Uint8Array(buf.length - 35 + 16);
  joined.set(buf.subarray(35));
  joined.set(buf.subarray(19, 35), buf.length - 35);
  return crypto.subtle.decrypt({ name: 'AES-GCM', iv: buf.slice(7, 19), tagLength: 128 }, await getKey(), joined);
}

const cache = new Map<string, Promise<string>>();

/** 图片地址 → 能直接给 <img src> 的 blob: 地址；同一地址只下载、解密一次 */
export function resolveImageUrl(url: string): Promise<string> {
  const hit = cache.get(url);
  if (hit) {
    cache.delete(url);
    cache.set(url, hit); // 挪到最新
    return hit;
  }
  const p = fetch(url, { mode: 'cors', credentials: 'omit' })
    .then((r) => {
      if (!r.ok) throw new Error(`http ${r.status}`);
      return r.arrayBuffer();
    })
    .then(decodeImage)
    .then((plain) => URL.createObjectURL(new Blob([plain])));
  p.catch(() => cache.get(url) === p && cache.delete(url)); // 失败不缓存，下次重试
  cache.set(url, p);

  if (cache.size > MAX_CACHE) {
    const [oldUrl, oldP] = cache.entries().next().value!;
    cache.delete(oldUrl);
    oldP.then((u) => URL.revokeObjectURL(u), () => {});
  }
  return p;
}

```

PC 端 React：用 `<HcImage>` 替换 `<img>`，所有显示 bbsv2 图片的地方都换掉。

```tsx
// HcImage.tsx
import { useEffect, useRef, useState, type ImgHTMLAttributes } from 'react';
import { resolveImageUrl } from './hcImage';

type Props = ImgHTMLAttributes<HTMLImageElement> & { fallback?: string };

/** 进入可视区才下载、解密（列表页不会一次拉几十张）；明文图同样能显示；失败显示 fallback */
export function HcImage({ src, fallback = '/img/placeholder.png', ...rest }: Props) {
  const ref = useRef<HTMLImageElement>(null);
  const [visible, setVisible] = useState(false);
  const [shown, setShown] = useState<string>();

  useEffect(() => {
    const el = ref.current;
    if (!el || visible) return;
    const io = new IntersectionObserver(
      ([e]) => {
        if (e.isIntersecting) {
          setVisible(true);
          io.disconnect();
        }
      },
      { rootMargin: '200px' },
    );
    io.observe(el);
    return () => io.disconnect();
  }, [visible]);

  useEffect(() => {
    if (!src || !visible) return;
    let alive = true;
    setShown(undefined);
    resolveImageUrl(src).then(
      (u) => alive && setShown(u),
      () => alive && setShown(fallback),
    );
    return () => {
      alive = false;
    };
  }, [src, visible, fallback]);

  return <img ref={ref} src={shown ?? fallback} {...rest} />;
}

// 用法：<HcImage src={thread.picture[0]} alt="" className="thumb" />
```

  再把 blob 地址交给它们；直接给原地址会是裂图。

  不适合直接拿来渲染接口数据。

```dart
// Flutter：pubspec 加 cryptography（建议同时加 cryptography_flutter，走系统原生 AES，大图解密不卡）
import 'dart:typed_data';
import 'package:cryptography/cryptography.dart';

final _key = SecretKey(hexToBytes(KEY_HEX));

/// 明文原样返回；密文解密后返回；解不开返回 null（显示占位图）
Future<Uint8List?> decodeImage(Uint8List buf) async {
  final isEnc = buf.length >= 35 && String.fromCharCodes(buf.sublist(0, 6)) == 'HCIMG1' && buf[6] == 1;
  if (!isEnc) return buf;
  try {
    final plain = await AesGcm.with256bits().decrypt(
      SecretBox(
        Uint8List.sublistView(buf, 35),                       // 密文
        nonce: Uint8List.sublistView(buf, 7, 19),             // IV
        mac: Mac(Uint8List.sublistView(buf, 19, 35)),         // tag，cryptography 单独传，不用拼在密文后面
      ),
      secretKey: _key,
    );
    return Uint8List.fromList(plain);
  } catch (_) {
    return null;
  }
}
// 显示：Image.memory(bytes)
```

- Flutter：用 `cached_network_image` 时，可以给它的 `cacheManager` 配自定义 `FileService`（flutter_cache_manager 的 `Config(fileService: …)`），
  在下载完成后调用 `decodeImage`，这样磁盘缓存里存的就是明文，列表里照常用 `CachedNetworkImage`。用 `pointycastle` 也行：
  `GCMBlockCipher(AESEngine())`、`AEADParameters(KeyParameter(key), 128, iv, Uint8List(0))`，`process(密文 + tag)`。
- Android：`Cipher.getInstance("AES/GCM/NoPadding")`，`GCMParameterSpec(128, iv)`，`doFinal(密文 + tag)`（同样要把 tag 接在密文后面）。
- iOS：CryptoKit `AES.GCM.SealedBox(nonce: AES.GCM.Nonce(data: iv), ciphertext: 密文, tag: tag)`，再 `AES.GCM.open(box, using: key)`。

**注意**

- 解不开（文件损坏、被篡改，GCM 校验失败）时显示占位图，不要让页面崩掉。
- 建议缓存**解密后**的图片（内存 / 磁盘均可），按图片地址做 key；同一个地址的内容不会变（审核命中换打码图时地址也会变）。
- H5 / PC 用 `fetch` 取字节，需要图片所在 CDN 返回跨域头（`Access-Control-Allow-Origin`），否则拿不到字节；这由运维配置。
  `fetch` 不要带 `credentials: 'include'`（跨域头是 `*` 时会被浏览器拒掉）。
- 浏览器只在安全上下文里提供 `crypto.subtle`：`https://` 或 `localhost` 下才有，用 `http://内网 IP` 打开页面调试时它是
  `undefined`，所有密文图都会走 fallback。
- 密钥本来就随客户端下发，这层加密只是让图片地址拿到别处打不开，不是访问控制，不用当成机密保管。
- **自测向量**（各端通用）：把下面这串 base64 解码成字节后交给解密函数，结果按 UTF-8 解读应为 `falive-bbsv2-imagecrypt-compat`。
  它是嗨聊那边的加密类实际跑出来的，能解对再拿真实图片地址测。

  ```text
  SENJTUcxAYg3OW3+jHXkeLQKleGW3fpiRXaLMpJ8j4NuquwEd2/bWPKmc3fz016csnyxuI0SjaxcQW64ijafthg=
  ```

  浏览器控制台：`new TextDecoder().decode(await decodeImage(Uint8Array.from(atob('SENJ…'), (c) => c.charCodeAt(0)).buffer))`。

## 2. 接口详情

以下按控制器分组。「鉴权」列：公开 = 不需要 Token 也能访问；需登录 = 必须带有效 Token，否则 `-700`。

### 2.1 CIndex（首页 / 健康检查）

#### `GET /bbsv2/index/index` — 心跳：模块健康检查 + 社区账号检查（公开）

无参数。可带登录 Token，也可不带。

**用途（PM-2954 新增）**：前端主动请求，为 live 已登录用户检查社区（Discuz）账号是否已开通，没有就当场开通（或认领嗨聊已开的号），已有则同步昵称与头像。社区 uid 为 Discuz uid，不等于 live 用户 id。
建议在进入社区页、App 切回前台时调用，不必等到用户第一次发帖或关注才开通。已开通的用户重复调用不查库、不写库，可以放心频繁调用。

响应 `data`：

| 字段 | 类型 | 说明 |
|---|---|---|
| module | string | 固定 `"bbsv2"` |
| status | string | 固定 `"ok"` |
| community | object | 社区账号检查结果，见下表 |

`community`：

| 字段 | 类型 | 说明 |
|---|---|---|
| state | string | 状态，取值见下表 |
| registered | int | 社区账号是否可用：`1` 可用（`state` 为 `ready` 或 `created`）/ `0` 不可用 |
| dz_uid | int | 社区 uid（Discuz uid，不等于 live 用户 id），仅供排查，其他社区接口不收也不返回这个值；不可用时为 `0` |

`community.state` 取值：

| 值 | 含义 | 前端处理 |
|---|---|---|
| `guest` | 未带 Token、Token 无效或游客 | 不开通；登录后再调 |
| `ready` | 已有社区账号，本次已按需同步昵称与头像 | 正常使用 |
| `created` | 本次新开通了社区账号 | 正常使用 |
| `pending` | 同一用户正在另一个请求里开通 | 稍后再调一次 |
| `cooling` | 最近一次开通失败，冷却中（约 10 秒） | 稍后再调一次 |
| `ineligible` | 不具备社区资格（机器人账号、直播库查无此人） | 不再重试 |
| `failed` | 开通或确认时发生异常（服务端已记日志） | 稍后再调一次 |

**响应示例**（已登录、首次开通）：

```json
{ "code": 0, "msg": "", "data": { "module": "bbsv2", "status": "ok",
  "community": { "state": "created", "registered": 1, "dz_uid": 62372 } } }
```

**响应示例**（未登录）：

```json
{ "code": 0, "msg": "", "data": { "module": "bbsv2", "status": "ok",
  "community": { "state": "guest", "registered": 0, "dz_uid": 0 } } }
```

> 兼容性：只新增了 `community` 字段，`module` / `status` 不变，旧版客户端不受影响。生产环境响应仍按 1.3 走 `sec`，不要依赖明文 `data`。

#### `GET /bbsv2/index/recommend` — 首页推荐聚合（公开，未登录也可访问）

一次拿热门帖子（今日推荐）+ 推荐作者 + 推荐帖子三栏，各自独立条数上限。未登录时 `recommend_authors[].is_follow`
恒为 `0`。登录态下 `recommend_authors` 候选池排除当前登录用户自己，不会出现"推荐关注自己"；
候选池会随机打散顺序再截取 `author_limit` 条，不保证严格按 `thread_count` 排序展示。
`hot_threads`/`recommend_threads` 结构完全相同（都同 2.3 `thread/listCursor` 的列表项），只是**入选依据**不同：

- `hot_threads`（今日推荐）：按 `views`（浏览数）挑出最热的帖子，**返回顺序为发布时间倒序**（`dateline desc`），
  不按 views 排。
- `recommend_threads`（推荐帖子）：读 Discuz 后台的**版主推荐**（「版块编辑 → 扩展设置 → 推荐主题」逐个版块开启，
  手动 / 自动 / 半自动三种方式），平台下各版块的推荐按 `forum/list` 的版块顺序拼接，**保持推荐顺序**（不是时间倒序）；
  版主推荐时改过短标题的，`subject` 返回短标题。后台改了推荐最多约 1 分钟后生效。**平台下没有任何版块开启推荐时**，
  兜底按 `replies`（评论数）挑选、发布时间倒序返回；开启了但还没有推荐内容时返回空数组。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| thread_limit | int | 否 | 5 | 热门帖子（按浏览数）条数上限（≤50） |
| author_limit | int | 否 | 4 | 推荐作者条数上限（≤50） |
| recommend_limit | int | 否 | 3 | 推荐帖子条数上限（≤50） |

| 字段 | 类型 | 说明 |
|---|---|---|
| hot_threads | 帖子列表项[] | 今日推荐，按 `views`（浏览数）降序，结构见 2.3 `thread/listCursor` 的列表项 |
| recommend_authors | array | `uid` `nickname` `avatar` `groupid` `group_title`（用户组名称）`thread_count`（当前平台发帖数）`is_follow`（当前登录用户是否已关注该作者，未登录恒为 0） |
| recommend_threads | 帖子列表项[] | 推荐帖子，读版主推荐、按推荐顺序（未开启推荐时兜底按评论数挑选），结构同 `hot_threads` |

#### `GET /bbsv2/index/recommendAuthorsCursor` — 推荐关注作者「换一批」游标翻页（公开）

跟 `index/recommend` 里固定的 Top-N 并存，用于"换一批"交互；未登录也可访问，此时 `is_follow` 恒为 `0`。
登录态下候选池同样排除当前登录用户自己。游标是"上一条的 `thread_count`"（发帖数并列时可能有极小概率
漏取/重取，量级上可忽略）；每页返回的候选集合按 `thread_count` 选出后会随机打散展示顺序（不影响
翻页游标与"取完"判断），避免反复"换一批"时靠前几位作者总是一样。

传 `tid` 时复用同一套翻页给**帖子详情页「相关作者换一批」**用：候选优先收窄到该帖子标签命中的作者
（不含帖子作者本人，口径同 `thread/related` 的 `related_authors`）；标签命中的候选不够时会回退用
平台发帖数最多的作者补位，**保证"换一批"恒有数据、不会返回空列表**（除非整个平台确实没有其它
作者这种极端情况）。补位候选一开始就并入同一份候选池统一按 `thread_count` 排序再翻页，不是翻到
最后才临时拼接，所以不会出现"前几批是标签命中、后面突然混入不相关作者"的观感。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| last_cursor | int | 否 | 0 | 上一页最后一条的 `thread_count`，不传/0=第一页 |
| per_page | int | 否 | 4 | 每页条数（≤20） |
| tid | int | 否 | 0 | 详情页场景传当前主题 ID，收窄候选到该帖子标签命中的作者；`0`=不收窄（首页场景）。不存在/不属于当前平台报 `BBSV2_THREAD_NOT_EXIST`；该主题的可见范围跟 `thread/detail` 一致（作者本人登录时自己被关闭 / 待审核 / 未通过的帖子也算存在，见 2.3），候选作者池本身仍是公开口径 |

响应 `data`：`list[]`（结构同 `index/recommend` 的 `recommend_authors`）`next_cursor`（这里是
`thread_count`，见 1.5）。

**响应示例**：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "list": [
      {"uid": 20003, "nickname": "阿超", "avatar": "https://cdn.example.com/avatar/20003.png", "groupid": 3, "group_title": "普通会员", "thread_count": 9, "is_follow": 0}
    ],
    "next_cursor": 9
  }
}
```

### 2.3 CThread（帖子）

> ⚠️ 帖子列表**只有游标翻页**，没有 `page` 分页版本（见 1.5），固定按 `tid desc`（约等于发表时间倒序），
> 不支持自定义排序。按热度/浏览量排序用 `thread/hot`（热门榜，非分页一次性返回，见下）；需要 `page`
> 分页的"我的帖子"类列表用 `member/threads`（见 2.6）。

#### `GET /bbsv2/thread/listCursor` — 帖子列表（公开，`type=2` 草稿需登录，游标翻页见 1.5）

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| last_id | int | 否 | 0 | 上一页最后一条的 `tid`，不传/0=第一页 |
| per_page | int | 否 | 10 | 每页条数（≤50） |
| fid | int | 否 | 0 | 版块 ID，`0` = 平台全部可见版块 |
| keyword | string | 否 | '' | 标题关键词 |
| digest | int | 否 | 0 | `>0` 仅精华 |
| uid | int | 否 | 0 | 按作者的 live 用户 ID 筛选，传了会自动等价于 `type=1`；对方还没有社区账号时列表为空 |
| type | int | 否 | 0 | `0`=公开列表 `1`=某作者公开列表（需配合 `uid`）`2`=我的草稿（需登录，只能看自己） |
| media_type | int | 否 | 0 | 内容类型筛选，见 1.6，`0`=不筛选 |
| tag_id | int | 否 | 0 | 按标签筛选（`forum/hotTags` 拿到的 `tagid`），`0`=不筛选 |

`type=2`（草稿箱）时必须带 Token，且只能看自己的草稿，传别人的 `uid` 会报 `BBSV2_DRAFT_FORBIDDEN`。
**没有** `order`/`sort` 参数，不支持自定义排序。

响应 `data`：`list[]`（`MRespBbsv2ThreadList`，下表）`next_cursor`（见 1.5）。这套列表项结构是
`thread/hot`、`thread/related` 的 `related_threads`、`member/threads`/`threadsCursor`、
`search/thread`/`threadCursor`（不含 `last_comment`，见 2.5）、`index/recommend` 的
`hot_threads` 共用的口径：

| 字段 | 类型 | 说明 |
|---|---|---|
| tid / fid / typeid | int | 主题 ID / 版块 ID / 分类 ID |
| subject | string | 标题 |
| author | object | `uid`（作者的 live 用户 ID，没有 live 用户时为 `0`）`nickname` `avatar` `groupid` `group_title`（用户组名称） |
| authorid | int | 作者的 live 用户 ID，同 `author.uid`；作者没有 live 用户时为 `0`（头像、昵称不可点） |
| dateline | int | 发表时间戳 |
| views / replies / heats / recommend | int | 浏览数 / 回复数 / 热度 / 点赞数 |
| digest | int | 精华等级：`0`=非精华，`1`/`2`/`3`=精华 I / II / III（Discuz 后台设置），`>0` 即可显示「精华」角标 |
| closed | int | 是否关闭（`1`=后台已关闭。公开列表不会出现关闭的帖子，只有作者本人的「我的帖子」可能带出，见 2.3 `thread/detail`） |

#### `GET /bbsv2/thread/detail` — 帖子详情（公开）

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| tid | int | 是 | - | 主题 ID |
| comment_id | int | 否 | 0 | 从"我的评论"（`member/threads`/`threadsCursor` 的 `type=commented`）跳转过来时，携带那条评论的 `pid`；配合响应 `my_comment` 字段展示"你的评论"卡片，不传/0=非该场景跳转 |

不存在/不属于当前平台 → `BBSV2_THREAD_NOT_EXIST`，且 **`code` 固定为 `-3`**（不是默认的 `-1`），客户端
可直接按 `code === -3` 落"帖子不存在"页。**调用会触发浏览数 +1**，返回的 `views` 已包含这次。
未登录也可访问（公开接口）。

**可见范围**：公开只能看已发布的帖子；**作者本人登录后**额外能看自己的待审核 / 未通过帖（从「我的帖子」
`audit_status=2/3` 的卡片点进来），响应 `audit_status` 同列表项口径（`1`=已发布 `2`=待审核 `3`=未通过），
前端据此在详情页顶部显示「审核中 / 未通过」状态条。别人访问这些帖仍按不存在处理（`-3`）。非已发布的帖
**不计浏览数**。

**被后台关闭的帖子**（`closed=1`）同理：只有作者本人能看详情和评论列表（`post/list`/`listCursor`/`listNewCount`），
响应 `closed=1`，前端据此隐藏回复框（回复会报 `BBSV2_THREAD_CLOSED`）；别人访问按不存在处理（`-3`）。关闭的帖子
也不会出现在信息流、版块列表、作者公开列表、搜索、热榜、首页推荐、相关推荐、赞过 / 收藏过 / 评论过列表里，
作者本人的「我的帖子」（`member/threads`/`threadsCursor` 的 `type=posts`）照常带出。

响应 `data.thread`（`MRespBbsv2ThreadDetail`）：字段基本同列表项，但**没有** `typeid`/`url`/`last_comment`；
`message` 是纯文本全文且**保留发帖时的段落换行**（`\n`，连续多个空行折叠为一个空行；列表项的
`message` 则合并成单行）；额外多 `pid`（首帖 pid）；`picture`/`video` 口径跟
`thread/listCursor` 完全一致（无图/无视频时分别是空数组），但详情里 `picture` / `video[].cover` 恒为原图 /
原封面（详情页看大图，列表接口才用缩略图覆盖），以及：

| 字段 | 类型 | 说明 |
|---|---|---|
| audit_status | int | 审核状态，口径同列表项：`1`=已发布 `2`=待审核 `3`=未通过。只有作者本人登录查看自己的帖子时才会出现 `2`/`3`（见上方"可见范围"），其余场景恒为 `1` |
| is_liked | int | 当前登录用户是否已点赞该帖，`1`/`0`；**未登录时恒为 `0`** |
| is_favorited | int | 当前登录用户是否已收藏该帖，`1`/`0`；**未登录时恒为 `0`** |
| favid | int | 当前登录用户对本帖的收藏 ID，未收藏/未登录恒为 `0`；取消收藏（`favorite/remove`）直接传这个，不用再翻 `favorite/list` 找 |
| favorite_count | int | 帖子总收藏数（不分用户），未登录也能看到真实值。**以社区收藏关系表实时统计为准**，与 Discuz 网页端显示的收藏数（其自身维护的 `favtimes` 计数字段）可能不一致，App 只认本接口 |
| content_locale | string | `subject`/`message` 当前实际所属语言，见下方"多语言内容"说明 |
| source_locale | string | 探测到的原文语言，仅当前内容为译文时有值，否则为空字符串 |
| my_comment | object\|null | 见下；未传 `comment_id`、未登录、或该 pid 不存在/不属于当前登录用户/不属于当前主题，恒为 `null` |

**多语言内容**：`subject`/`message` 已经是按当前请求语言（跟 App 当前显示语言态一致，无需额外传参）
直接返回的最终展示内容——命中翻译时就是译文，没有翻译（或翻译还没跑完）时就是原文，App 侧只管展示这两
个字段，不需要自己判断"要不要显示译文"或做二次切换。`content_locale`/`source_locale` 只是附带的次要
信息，用于展示"机翻"角标之类的 UI 提示（比如 `content_locale` 不等于内容原本语言时加个"机器翻译"标记），
不参与主流程判断，也不影响 `subject`/`message` 本身的展示逻辑。当前不支持"查看原文"（无法在同一条内容
上切换回原文）。**只翻 2026-11-01 00:00（北京时间）起发的帖子 / 评论**，更早的不再机翻，展示原文（已经翻好的译文照常返回）。

请求语言的判断顺序跟全站文案一致：URL 参数 `vn_lang` → 请求头（`x-accept-language` 优先，其次
`Accept-Language`）→ cookie `vn_lang`。中文展示原文（`content_locale` 为 `zh-cn`），不区分大小写、下划线等同连字符，`zh`、`zh-Hans`、`zh-Hans-CN`、`zh-SG` 都算简体，`zh-TW`、`zh-Hant`、`zh-HK` 都算繁体；
三者都没有（如分享链接被外部浏览器直接打开），或带了不受支持的语言时，展示原文（跟全站默认语言简中一致）。
站点支持、但社区没有做机翻的语言（如泰文）同样展示原文（2026-10-09 前会显示越南文译文）。
帖子内容、用户组称号（`group_title`）、标签名、积分类型 / 任务名称的多语言都按这个规则，App 切换语言后
请保证上面三者之一带的是新语言（推荐统一带 `x-accept-language`）。注意 `Accept-Language` 一般是系统 / 浏览器
语言，只靠 cookie 切语言、又带着系统 `Accept-Language` 时，会按系统语言展示。

**用户等级称号带 emoji（2026-10-03）**：社区用户等级 L1~L8 的 `group_title` 前面带等级 emoji，emoji 跟称号之间是一个半角空格，

#### `GET /bbsv2/thread/related` — 帖子详情页「相关作者 + 相关推荐」（公开）

对应帖子详情页侧栏「相关作者」「相关推荐」两个卡片，一次接口拿两组数据。未登录也可访问，此时 `related_authors[].is_follow` 恒为 `0`。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| tid | int | 是 | - | 当前查看的主题 ID |
| author_limit | int | 否 | 4 | 相关作者条数上限（≤20） |
| thread_limit | int | 否 | 4 | 相关帖子条数上限（≤20） |

`tid` 不存在/不属于当前平台 → `BBSV2_THREAD_NOT_EXIST`。当前主题的可见范围跟 `thread/detail` 一致（见 2.3）：
作者本人登录时，自己被关闭 / 待审核 / 未通过的帖子也算存在，从「我的帖子」点进详情页时本接口不会反过来报不存在；
别人访问这些帖仍是 `BBSV2_THREAD_NOT_EXIST`。`related_threads` 候选池本身仍是公开口径，不会带出非公开帖。

**候选与排序规则**：先按当前主题挂的标签找候选（同标签的其它作者 / 其它帖子）。`related_authors` 按
**粉丝数从高到低**排序；标签命中数不够 `author_limit` 时，用「当前平台发帖数最多的作者」补位凑够数量，
补位后跟标签命中结果合并、按粉丝数重新整体排序（不是简单拼接在后面）——最终列表里任意一条都可能来自
"标签命中"或"补位"，App 侧不需要也无法区分来源。`related_authors` 天然不含当前主题的作者本人（自己给
自己"关注推荐"没有意义）。

`related_threads` 先按标签命中取一份候选池（标签命中不够时，用「当前平台浏览量最高的帖子」补齐
候选池），候选池**按发布时间倒序稳定排序后截取前 `thread_limit` 条**（bbsv2 所有帖子列表统一时间倒序；
2026-09-25 前是随机打散，现已改为稳定排序，同样的数据两次请求结果一致）。`related_threads` 不含当前
主题本身，但可能包含同作者的其它帖子（只看标签是否相关，不管是不是同一个作者）。极端
情况下（平台内容很少）两个列表都可能不足 `xxx_limit` 条甚至为空，App 侧按空列表处理，不需要额外报错。

#### `POST /bbsv2/thread/create` — 发帖（需登录）

无需传 `fid`，帖子固定落到当前平台的第一个圈子（按显示序、版块 ID 升序，跟嗨聊发帖同一口径；走该圈子
自己的 `modnewposts` 审核配置：0=发帖/回帖都不审 1=发帖审回帖不审 2=发帖/回帖都审）；该平台还没有
圈子时回 `BBSV2_FORUM_NOT_EXIST`，服务端不再自动建版块（圈子及其平台归属在 Discuz 后台维护）。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| subject | string | 是 | - | 标题，1~80 字符 |
| content | string | 否 | '' | 纯文本正文（换行用 `\n`，不含图片/视频），带图/视频时可为空 |
| images | int[] | 否 | [] | 图片附件 aid 数组（先 `tool/upload`），按顺序展示；最多 5 张，超过报 `BBSV2_IMAGES_TOO_MANY` |
| video | int | 否 | 0 | 视频附件 aid，`0`=无视频 |
| tags | int[] | 否 | [] | 标签 tagid 数组，最多 5 个（见 1.7） |

`content` 为空且 `images`/`video` 都为空，或正文含 `<script>` 等危险标签/事件属性 → `BBSV2_MESSAGE_INVALID`；
`images`/`video` 传了不存在或不属于自己的 aid → `BBSV2_ATTACHMENT_INVALID`；标题为空或超 80 字符 →
`BBSV2_SUBJECT_INVALID`。版块开了新帖审核时，帖子会进入待审状态（见响应 `pending`），列表/详情暂时看不到。

发布资格（`post/create` 同规则，最先检查）：账号被 Discuz 后台「禁止发言」「禁止访问」或「锁定」→
`BBSV2_USER_BANNED`，带期限的禁止报 `BBSV2_USER_BANNED_UNTIL`（文案含解禁时间，到期后自动恢复）；所在用户组在
后台没有发帖权限 → `BBSV2_GROUP_NO_POST_PERMISSION`（回复看回复权限，报 `BBSV2_GROUP_NO_REPLY_PERMISSION`）。
后台禁止 / 解禁立即生效。

标题/正文会过一遍后台「全局 -> 关键字过滤」的规则（跟旧版 Discuz 社区站共用同一份词库）：命中违禁词直接拒绝
发布 → `BBSV2_CONTENT_BANNED`；命中审核词不拒绝，但会强制把 `pending` 置为 `1`（即便版块本身没开审核
也照样送审）；命中普通替换词会被静默替换成规则里配置的替代文本，不影响发布/审核状态，落库/响应里的
正文已经是替换后的结果。

正文还会过一遍字数下限/上限 + 发帖间隔限制 + 重复提交拦截（见 1.9）：命中分别报 `BBSV2_CONTENT_TOO_SHORT` /
`BBSV2_CONTENT_TOO_LONG` / `BBSV2_POST_TOO_FREQUENT` / `BBSV2_DUPLICATE_SUBMIT`；带图/视频、`content` 传空串时跳过字数下限检查。

响应 `data.thread`：`tid` `pid`（首帖 pid）`subject` `dateline` `pending`（`1`=待审，暂不可见；`0`=已发布）。

**响应示例**：

```json

  "code": 0,
  "msg": "Operation successful",
  "data": { "thread": { "tid": 10088, "pid": 12000901, "subject": "求推荐一部好看的电影", "dateline": 1758000000, "pending": 0 } }
```

### 2.6 CMember（会员中心，全部需登录）

- 登录了、但自己的社区账号没开通成功时，本节接口大多报 `BBSV2_USER_NOT_EXIST`；`member/otherInfo` 和 `member/threadsCount`
  看他人时例外，照常返回（我对 TA 的 `is_follow` / `mutual` 为 `0`）；`member/follow` 取关提示「请稍后再试」（`Network busy`，2026-10-20 起）。
- 只算当前平台的：`liked_count` / `favorited_count`、`member/threads*` 列表与计数、`threadsCount` 的帖子类四项；
  不分平台的：积分、用户组、关注 / 粉丝、新手任务，以及资料里的 `threads` / `posts` 计数器。
- 「我的关注」合并了直播端关注：在直播端关注接口、社区 `member/follow` 关注 / 取关，关注列表、关注数（`following`）和
  `friendsNewCount(type=follow)` 都立即生效（2026-10-20 起，以前直播端的最多晚 10 分钟）；只有后台等别的途径直接改了直播端关注时，
  最多 10 分钟后才体现。
- 本节的 `member/threads*` 只能看自己；他人的帖子用 `thread/listCursor?uid=`，他人的 tab 条数用 `member/threadsCount?uid=`。

#### 个人主页各 tab 对应接口

|---|---|---|---|
| 头部资料（昵称、头像、等级、关注 / 粉丝数） | — | 自己：`member/info`；他人：`member/otherInfo?uid=` | 同左 |

#### `GET /bbsv2/member/otherInfo` — 他人资料

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| uid | int | 是 | 目标的 live 用户 ID（帖子作者、关注列表等社区接口返回的 `uid`，或热门主播等直播侧拿到的主播 id）。直播侧查无此人（含游客 id）报 `BBSV2_USER_NOT_EXIST` |

对方是主播、还没有社区账号时，服务端当场替对方开通，照常返回资料。对方没有社区账号（不是主播且没进过社区，或开通暂未完成），

`title`（直播间标题）`starttime`（开播/预约时间戳）。

/ `live` 与 `level_card` 里的直播等级卡（`type=2`）照常取直播侧；社区侧字段一律为默认空值——`groupid` / `regdate`
/ `credits` / `friends` / `threads` / `posts` / `replies` / `is_follow` / `mutual` 为 `0`，
`group_title` 为 `""`；`level_card` 里**不放**社区等级卡（`type=1`），只有直播等级卡一张。`follower` / `following`：
对方**没有社区账号**时 `following` 为 `0`（直播端的关注不计），`follower` 只有直播粉丝数；有社区账号、只是资料行缺失时两项照常按综合口径算。`level_card` 的卡片请按

> ⚠️ 本接口是「关注/粉丝列表」唯一入口，没有 `page` 分页版本。

固定按关系建立时间倒序。`type=follow`（我的关注）同时包含**直播端关注的主播**（社区关注与直播端关注
按关注时间合并排序；两边的关注接口关注 / 取关立即体现，后台等别的途径直接改了直播端关注的最多晚 10 分钟）；`type=fan`（我的粉丝）只含社区侧
关注关系。`last_id`/`next_cursor` 语义是"上一条的关系建立时间戳"（不是 uid），见 1.5 的边界说明。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| type | string | 否 | follow | `follow`=我的关注（含直播端关注的主播） \| `fan`=我的粉丝（区分大小写，其它值报 `BBSV2_FRIEND_TYPE_INVALID`） |
| last_id | int | 否 | 0 | 上一页最后一条的关系建立时间戳，不传/0=第一页 |
| per_page | int | 否 | 20 | 每页条数，`[1, 50]` |

响应 `data`：`list[]`（`MRespBbsv2MemberFriend`：`uid`（对方的 live 用户 ID，纯直播端关注、对方还没有社区账号时也有值；对方只有社区号、没有 live 用户时为 `0`，头像不可点）
`username`（昵称，直播资料优先）`avatar` `groupid` `group_title` `following` `follower`（**对方的社区关注数 / 社区粉丝数**，
不是 `member/info` 那种社区 + 直播综合计数；纯直播端关注、对方没有社区账号的行为 `0`）`is_follow`（我是否
关注对方，`fan` 场景下用于判断"回关"）`follow_type`（我对 TA 的关注在哪边，见下表）`mutual`（是否互相关注，只看社区，纯直播端关注对方恒为 `0`）
`dateline`（建立关系时间戳；两边都关注的人取较新的那次）`is_anchor`（是否为主播，仅 `type=follow` 会计算真实值，`fan` 恒为 `0`）
`live`（结构同 `member/otherInfo` 的 `live`，`is_anchor=0` 时为占位默认值）`is_writer`（是否作者，即对方
已同步社区资料；纯直播端关注、对方还没有论坛账号时为 `0`，`fan` 恒为 `1`）） + `next_cursor`（这里是时间戳，见 1.5）。

**响应示例**：

```json
{
  "code": 0,
  "msg": "Operation successful",
  "data": {
    "list": [
      {"uid": 300002, "username": "小美", "avatar": "https://cdn.example.com/avatar/300002.png", "groupid": 3, "group_title": "普通会员", "following": 6, "follower": 8, "is_follow": 1, "follow_type": "both", "mutual": 0, "dateline": 1758000000, "is_anchor": 1, "live": {"anchor_id": 300002, "live_id": 88001, "status": 1, "title": "今晚陪你聊聊天", "starttime": 1758005000}, "is_writer": 1}
    ],
    "next_cursor": 1758000000
  }
}
```

`follow_type`（string）：

| 值 | 含义 |
|---|---|
| `community` | 只在社区关注 |
| `live` | 只在直播端关注 |
| `both` | 两边都关注 |
| `none` | 此刻两边都没关注，这时 `is_follow` 同为 `0`。`type=follow` 列表由社区、直播两边的关注接口当场刷新；只有后台等别的途径改了关注时，列表最长 10 分钟才刷新，这期间还会列着 |

`follow_type` 按请求当下两边的关注记录算，不受列表刷新延迟影响。取关不用看它：`community` / `live` / `both` 一律调
`POST /bbsv2/member/follow`，`uid` 传列表项的 `uid`，`action=0`，两边一次取消（见该接口）；`none` 不用调，调了报 `BBSV2_FOLLOW_MISSING`。
**不要再调直播端 `/api/member/attention` 取关**：它是「已关注就取关、没关注就关注」的切换式接口，`member/follow` 已经取消过的再调一次会把两边的关注加回来。
`type=fan` 只看社区侧：回关了为 `community`，没回关为 `none`（只在直播端关注了这个粉丝的也是 `none`），回关调 `member/follow` `action=1`。

#### `GET /bbsv2/member/threads` — 我的主题关系列表（分页）

我的帖子 / 赞过的帖子 / 收藏的帖子 / 评论过的帖子，四个 Tab 共用一个接口，用 `type` 区分。**不含
"我的预测"**。游标翻页版本见下条 `member/threadsCursor` + 1.5。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| type | string | 否 | posts | `posts`=我的帖子 \| `liked`=我赞过的帖子 \| `favorite`=我收藏的帖子 \| `commented`=我评论过的帖子 |
| page | int | 否 | 1 | 当前页 |
| per_page | int | 否 | 10 | 每页条数，`[1, 50]` |
| audit_status | int | 否 | 0 | **仅 `type=posts` 生效**的状态筛选：`0`=全部 \| `1`=已发布 \| `2`=待审核 \| `3`=未通过（口径同列表项 `audit_status`，前端「全部/已发布/审核中/未通过」Tab 直接传）；其余 `type` 忽略该参数（传什么都不报错） |

`type` 不在上述四个取值内 → `BBSV2_MEMBER_THREAD_TYPE_INVALID`；`type=posts` 时 `audit_status` 不在 0/1/2/3 →
`BBSV2_MEMBER_AUDIT_STATUS_INVALID`（草稿 `4` 不在「我的帖子」里筛，走草稿箱）。

分页响应 `data.list[]`：结构同 `thread/listCursor` 的列表项（`MRespBbsv2ThreadList`，见 2.3），同样带当前用户的 `is_liked` / `is_favorited`。

- `liked`：按"我最近一次点赞的时间"倒序；`favorite`：按收藏先后倒序（同一帖收藏多次会去重，只出现一张
  卡片，按最近那次收藏排）；`commented`：按"我最后一次评论该帖的时间"倒序，只算正常显示的楼层回复（主题首帖不算，
  待审核 / 已删除的评论不算），在自己帖子下的回复也算。三者都只返回当前平台可见版块内**已发布且未关闭**的帖子。
- `posts` 是**作者本人视角**：返回我的全部投稿——已发布（含已关闭的）+ 待审核 + 未通过（审核忽略 / 被后台下架进回收站），
  按发表时间倒序（游标版 `threadsCursor` 按 tid 倒序），
  用列表项 `audit_status`（`1`=已发布 `2`=待审核 `3`=未通过）显示状态角标；已删除的帖子不返回，草稿走
  `thread/listCursor` 的 `type=2` 草稿箱，也不混进来。跟 `thread/listCursor` 的 `type=1`（作者公开列表，
  别人看到的）区别就在这里：公开列表只有已发布。待审核 / 未通过的帖子**作者本人登录后**可以正常跳
  `thread/detail` 看详情（详情响应也带 `audit_status`，见 2.3），别人访问仍按不存在处理（`-3`）。
- `commented` 卡片额外带 `last_comment`（`MRespBbsv2ThreadListLastComment`）：`pid`（评论 ID，跳详情用
  于定位楼层）`message`（评论内容摘要）`dateline`（评论时间戳）`recommend`（评论点赞数）`position`
  （楼层号，定位用）`reply_to_pid`（被回复的评论 ID，`0`=直接评论主题）`reply_to_author`（被回复评论的
  作者名，取社区帖子表里记录的名字，可能跟其它地方显示的直播昵称不一致）`reply_to_message`（被回复评论的内容摘要；后两项在 `reply_to_pid=0` 时为空串）。其余三种
  type 下 `last_comment` 恒为 `null`。

**响应示例**（`type=commented`）：

#### `GET /bbsv2/member/threadsCount` — 主页 tab 条数：帖子 / 收藏 / 赞过 / 评论过 + 关注数 / 粉丝数（会员中心 / 他人主页角标用）

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| uid | int | 否 | 0 | 目标的 live 用户 ID。不传 / `0` / 自己的 uid = 看自己；传他人 uid = 看他人（对方没有社区账号时帖子类各项为 `0`，见下） |

一次返回「帖子 / 收藏 / 赞过 / 评论过」四个 tab 的总条数（仅当前平台）以及关注数 / 粉丝数（不分平台）：

- **看自己**：前四项口径与 `member/threads` 各 `type` 的列表总数（`page.allCount`）完全一致。
- **看他人**：`posts` 只数**已发布且未关闭**的帖子，跟 `thread/listCursor?uid=他人` 的作者公开列表条数一致（待审核 /
  未通过 / 草稿 / 已关闭都不计）；他人的收藏 / 赞过 / 评论过不对外，`favorite` / `liked` / `commented` 恒为 `0`。
- **关注数 / 粉丝数**：自己和他人同一口径，都是**社区 + 直播的综合计数**，跟 `member/otherInfo`（看自己时
  `member/info`）返回的 `following` / `follower` 完全一致：
  - 关注数：社区关注 + 直播端关注**按人去重**（同一个人两边都关注只算 1），**等于** `friendsCursor(type=follow)`
    列表的总条数。
  - 粉丝数：社区粉丝数 + 直播端粉丝数，**只合并数量、不去重**。粉丝列表 `friendsCursor(type=fan)` 只有社区粉丝，
    所以粉丝数通常**大于**粉丝列表条数。
- 看他人、对方没有社区资料时不报错，帖子类各项为 `0`：对方**没有社区账号**（纯直播用户）时 `following` 为 `0`、
  `follower` 只有直播粉丝数；有社区账号、只是资料行缺失时关注数 / 粉丝数照常按综合口径算；直播侧也查无此人时各项都是 `0`。
- 看自己、但自己没有社区资料 → `BBSV2_USER_NOT_EXIST`。

> 帖子数请用本接口的 `posts`，不要用 `otherInfo` 的 `threads`：后者是累计计数器，不区分审核状态、不分平台。

响应 `data.counts`（`MRespBbsv2MemberThreadsCount`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| posts | int | 帖子。看自己：作者本人视角，已发布（含已关闭）+ 待审核 + 未通过（不含草稿、已删除），同 `type=posts` 且 `audit_status=0`；看他人：只数已发布且未关闭的 |
| favorite | int | 收藏的帖子，同 `type=favorite`；看他人恒为 `0` |
| liked | int | 赞过的帖子，同 `type=liked`；看他人恒为 `0` |
| commented | int | 评论过的帖子（按帖子去重，一帖多条评论算 1），同 `type=commented`；看他人恒为 `0` |
| following | int | 关注数，社区 + 直播按人去重，等于 `friendsCursor(type=follow)` 列表总条数；同 `otherInfo` / `info` 的 `following` |
| follower | int | 粉丝数，社区粉丝数 + 直播粉丝数，不去重（粉丝列表只有社区粉丝）；同 `otherInfo` / `info` 的 `follower` |

#### `POST /bbsv2/member/follow` — 关注/取消关注

> **关注、取消都是两边一起做**：`action=1` 建社区关注，对方是主播时直播端也一起关注（2026-10-20 起）；`action=0` 把社区、直播两边的
> 关注一次取消（2026-10-19 起）。两边一起成功或一起失败。社区里的关注 / 取关**只调本接口**，不再调直播端 `/api/member/attention`，
> 也不用按 `follow_type` 选接口。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| uid | int | 是 | — | 对方 live 用户 ID（各接口返回的 `uid`） |
| action | int | 否 | 1 | `1` 关注 / `0` 取消 |

响应 `data` 为 `[]`，不带关注状态；需要最新状态时重新拉 `otherInfo` / `friendsCursor`，或按下面的结果表直接改本地状态。

```json
{ "code": 0, "msg": "Operation successful", "data": [] }
```

**关注状态从哪读**

社区有两套关注记录：**社区关注**和**直播端关注**。2026-10-20 起两个入口（本接口、直播间的关注按钮）都会两边一起写，但存量数据、
对方不是主播的关注、社区那边不具备条件时在直播间点的关注，仍可能只有一边，所以各入口给的关注状态口径不同：

| 入口 | 字段 | 口径 |
|---|---|---|
| 我的关注 `friendsCursor?type=follow` | `follow_type` / `is_follow` | 两边都看，按请求当下的关注记录算：`community` / `live` / `both` 为已关注，`none` 为未关注 |
| 我的粉丝 `friendsCursor?type=fan` | `follow_type` / `is_follow` | 只看社区：我是否回关了 TA（`community` / `none`） |
| 他人主页 `otherInfo` | `is_follow` / `mutual` | 只看社区关注；只在直播端关注了 TA 时为 `0` |
| 首页推荐作者 `index/recommend` 的 `recommend_authors[]`、`index/recommendAuthorsCursor` | `is_follow` | 只看社区关注；未登录恒为 `0` |
| 帖子详情相关作者 `thread/related` 的 `related_authors[]` | `is_follow` | 只看社区关注；未登录恒为 `0` |

按钮：已关注显示「已关注 / 取消关注」，点了调 `action=0`；未关注显示「关注」，点了调 `action=1`。

**关注（`action=1`）**

- 建**社区关注**；对方是**主播**时直播端也一起关注（直播间里对 TA 显示已关注，TA 的直播粉丝数 +1）。对方不是主播时只建社区关注。
- 只关注了一边的再点关注，把另一边补上：只在直播端关注了 TA（`follow_type=live`，他人主页 `is_follow=0`）的补上社区关注；
  社区已关注、直播端还没关注的主播（如 TA 成为主播之前关注的）补上直播端关注；`follow_type` 都变成 `both`。
  要关注的几边（对方是主播看两边，不是主播只看社区）都已关注才报 `BBSV2_FOLLOW_DUPLICATE`。
- 两边一起成功或一起失败；失败时原样重试，只补还没关注的那边，不会重复计数。
- 对方还没有社区账号：服务端当场替 TA 开通；开通暂未完成报 `BBSV2_USER_NOT_EXIST`，稍后重试。
- 成功后：
  - 对方的粉丝数立即 +1；我的关注数立即 +1（关注数按人去重，原本已在直播端关注 TA 的不变）；我的关注列表立即出现 TA；
    对方已经关注我时双方互关（`mutual=1`）。
  - 社区关注是这次新建的，给对方发一条 `follow` 类型的站内通知（互动类，`category=1`）；只补了直播端那边的不发。
    对方还没读的同一个人的关注通知只留一条：来回取关、再关注不会给对方刷出一串「关注了你」。
  - 不发新手任务「关注一位社区作者」的积分（2026-10-19 起由 Go 积分服务发放）；`member/noviceTask` 的「关注」项按社区关注数立即显示完成。

| 结果 | 建议提示 | 按钮 |
|---|---|---|
| 成功 | 关注成功 | 已关注 |
| `BBSV2_FOLLOW_DUPLICATE`（已关注） | 当成功处理 | 已关注 |
| `BBSV2_FOLLOW_NOT_ALLOWED` | 显示 `msg`（暂不允许关注） | 关注 |
| `BBSV2_USER_NOT_EXIST` | 显示 `msg`，可稍后重试 | 关注 |
| 其他错误、超时、没有响应 | 关注失败，请稍后重试 | 关注；用户再点时原样重试（上次其实成功了会报已关注，按成功处理） |

**取消关注（`action=0`）**

- 社区、直播两边的关注**一次取消**：服务端当场查两边的关注记录，有哪边删哪边，两边一起成功或一起失败，
  不会出现「一边取消了、一边还在」。
- 只删此刻还在的关注，**不做切换**：不会把已经取消的关注加回来，所以结果不确定时可以原样重试。
- 下面这些都调本接口：关注列表 `follow_type` 是 `community` / `live` / `both` 的、粉丝列表里已回关的、他人主页 / 推荐作者 / 相关作者 `is_follow=1` 的。
  对方还没有社区账号（只在直播端关注）也能取消，不会替 TA 开号。
- 成功后：我的关注数、对方粉丝数（社区、直播两边）立即减少；对方那条的互关标记清掉。不发通知，不动积分。
- **不要再调直播端 `/api/member/attention` 取关**：它是「已关注就取关、没关注就关注」的切换式接口，在本接口取消过的人身上再调一次会重新关注。

| 结果 | 建议提示 | 关注列表这一行 | 用户再点时 |
|---|---|---|---|
| 成功 | 已取消关注 | 移除 | — |
| `BBSV2_FOLLOW_MISSING`（尚未关注） | 当成功处理 | 移除 | — |
| 其他错误、超时、没有响应 | 取消关注失败，请稍后重试 | 保留，不改 `follow_type` | 原样再调一次 `action=0`，不用先刷新列表 |

> 两边的关注存在两个库里，服务端两边都写完才一起提交（关注、取消都是）。极少数情况下（社区库已提交、直播库提交时出错）只会写成社区那边，
> 这时接口照样返回失败，按上表重试一次就会把直播那边补上。

关注 / 取消成功后各处什么时候变：

| 位置 | 生效 |
|---|---|
| 关注列表、我的关注数、对方粉丝数（`info` / `otherInfo` / `threadsCount`） | 立即 |
| 直播间里对 TA 的关注状态 | 立即 |
| 直播端「我关注的主播开播状态」`/api/live/AttentionList` | 通常立即（服务端按请求的渠道号刷新这份缓存；渠道号对不上的那份最多晚 2 分钟） |

**跟直播端关注接口的关系**

- 直播端 `/api/member/attention`（直播间里的关注按钮）是切换式：按直播端此刻有没有关注 TA 切换，2026-10-20 起社区那边跟着一起变——
  关注时社区一起关注（对方还没有社区账号时服务端当场开通；开通暂未完成、或 TA 不允许被关注时只关注直播端，不报错），
  取消时社区的关注一起取消。两边一起成功或一起失败。社区页面不要调它（切换式，取消过的再调一次会把两边都关注回来）。
- 社区已关注、直播端没关注的人，在直播间点关注是「关注」（补上直播端），不会把社区关注取消。
- 在直播端关注 / 取关后，社区「我的关注」列表、关注数、对方粉丝数立即变。

**错误**

| lang key | 场景 |
|---|---|
| `BBSV2_FOLLOW_ACTION_INVALID` | `action` 不是 0 / 1 |
| `BBSV2_FOLLOW_SELF` | 关注 / 取关自己 |
| `BBSV2_USER_NOT_EXIST` | 直播侧查无此人（含游客 id）；关注时替对方开通暂未完成；关注时我自己的社区账号没开通成功 |
| `Network busy` | 「请稍后再试」：取关时我自己的社区账号还没开通成功（开通中或刚失败），稍后原样重试（2026-10-20 起，此前报 `BBSV2_USER_NOT_EXIST`） |
| `BBSV2_FOLLOW_NOT_ALLOWED` | 关注时对方设置了不允许被关注 |
| `BBSV2_FOLLOW_DUPLICATE` | 关注时已经关注过，按成功处理 |
| `BBSV2_FOLLOW_MISSING` | 取关时两边都没关注，按成功处理 |
| `BBSV2_FOLLOW_FAILED` | 写入失败（罕见），可重试 |

<a id="update-signature"></a>
#### `POST /bbsv2/member/updateSignature` — 修改个人简介

主页「关于」tab 里的「编辑简介」。简介就是直播端的个性签名，和直播端 `/api/member/updateInfo` 的 `signature` 是同一个字段，
改完两边一起变。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| signature | string | 否 | `""` | 新简介，前后空格会去掉。**传空串或不传 = 清空**（直播端 `updateInfo` 不能清空，这里可以） |

响应 `data`（`MRespBbsv2MemberSignature`）：`signature` 为保存后的简介，和之后 `member/info` 返回的一致，直接拿它刷新页面即可。

```json
{ "code": 0, "msg": "Operation successful", "data": { "signature": "看球十年，只聊足球" } }
```

- 保存后 `member/info`、`member/otherInfo`、帖子详情的相关作者 `signature` 立即是新值。
- 跟当前简介一样时不写库，照常返回成功。
- 敏感词：命中违禁词或审核词报 `BBSV2_CONTENT_BANNED`，整段不保存（简介没有送审流程）；命中普通替换词时，按后台配置替换后保存，
  返回的 `signature` 是替换后的内容。
- `< > & " '` 按 HTML 实体保存（同直播端），返回值也是转义后的（如 `&lt;`），按纯文本展示前先解码。已经是实体的不再转义
  （2026-10-20 起）：编辑框直接回填接口返回的值再保存，不会变成 `&amp;amp;`，内容没变就不写库。
- 最长 255 字，按保存后的字数算：`< > & " '` 转义后一个算 4～6 个字。超长报 `BBSV2_SIGNATURE_TOO_LONG`（`msg` 带上限），整段不保存。
- 不检查 Discuz 后台的禁止发言 / 锁定：简介就是直播端签名，直播端 `updateInfo` 也不拦，两边口径一致。
- 不触发新手任务。

| lang key | 场景 |
|---|---|
| `BBSV2_CONTENT_BANNED` | 简介命中违禁词或审核词 |
| `BBSV2_SIGNATURE_TOO_LONG` | 保存后超过 255 字 |

#### `GET /bbsv2/member/noviceTask` — 新手任务完成状态

固定 3 个任务项，完成状态由已有的关注 / 发帖数据推导判断。完成后的积分奖励
（后台积分策略 `novice_vote`/`novice_follow`/`novice_post`，每人每项仅一次）**2026-10-19 起由 Go 积分服务发放**，
本模块的 `member/follow`、`thread/create` 不再发放。**「完善个人资料」2026-10-19 起不再发放，并从列表拿掉**
（以前发放过的老用户也不再显示这一项），App 不要写死任务数。本接口只读，不发放积分。发放后会产生积分记录
（`member/credit`）与积分通知（`notify` 的 `credit` 类型）。`points` 取后台积分策略配置的奖励数（各积分类型之和；配置成 0 就显示 0，配置改动约 2 分钟内生效），规则
未配置时展示下表默认值。展示顺序即 `list[]` 顺序（投票 → 关注 → 发帖）：

| key | 名称 | 完成条件 | points（默认） |
|---|---|---|---|
| vote | 参加第一次投票 | 暂未开放，恒为未完成 | 100 |
| follow | 关注一位社区作者 | 社区关注数 > 0（只在直播端关注的不算，跟 `member/info` 的综合关注数不是一回事） | 10 |
| post | 发布第一篇帖子 | 主题数 > 0（全局计数，不分平台） | 50 |

无参数。响应：`data.info`（`MRespBbsv2NoviceTaskInfo`）`finished`(是否已全部完成) `total`(任务总数)
`done`(已完成数，**int**)；`data.list[]`（`MRespBbsv2NoviceTaskItem`）`key` `name` `done`（该项是否已完成，
**bool**，跟 `info.done` 的"已完成数"不是同一类型，注意区分）`points`（完成后奖励积分，取后台积分策略配置）
`target`（跳转标识，与 `key` 相同，App 按 `key` 维护路由映射表即可）。

**响应示例**：

```json
{
  "code": 0,
  "msg": "Operation successful",
  "data": {
    "info": {"finished": false, "total": 3, "done": 1},
    "list": [
      {"key": "vote", "name": "参加第一次投票", "done": false, "points": 100, "target": "vote"},
      {"key": "follow", "name": "关注一位社区作者", "done": true, "points": 10, "target": "follow"},
      {"key": "post", "name": "发布第一篇帖子", "done": false, "points": 50, "target": "post"}
    ]
  }
}
```

#### `POST /bbsv2/favorite/add` — 收藏帖子/版块

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | int | 是 | 收藏对象 ID（帖子传 tid，版块传 fid） |
| idtype | string | 是 | `tid` \| `fid` |

#### `POST /bbsv2/favorite/remove` — 取消收藏

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| favid | int | 否 | 0 | 收藏 ID，跟 `tid` 二选一传，优先传 `thread/detail`/`favorite/list` 返回的 `favid` |
| tid | int | 否 | 0 | 帖子 ID，跟 `favid` 二选一传；拿不到 `favid` 时可以只传 `tid`，服务端按当前登录用户反查该帖的收藏 ID 再删除（仅支持按 idtype=tid 反查，不支持按 fid 收藏取消） |

`favid`/`tid` 都不传或都 `<=0` → `Operation failed`；只传 `tid` 但反查不到当前用户对该帖的收藏 →
`BBSV2_FAVORITE_NOT_EXIST`。取消时会删除当前用户对该对象的全部收藏记录，取消后 `is_favorited` 必为 `0`。

**响应示例**：

```json
{ "code": 0, "msg": "Operation successful", "data": [] }
```

### 2.8 CTool（上传，全部需登录）

#### `POST /bbsv2/tool/upload` — 上传图片/视频附件

`multipart/form-data`，文件字段名固定 `file`。类型/大小限制见 1.8。

无文件 → `BBSV2_UPLOAD_NO_FILE`；类型不支持 → `BBSV2_UPLOAD_TYPE_INVALID`；图片总像素（宽×高）超过 5000 万 →
`BBSV2_UPLOAD_PIXEL_LIMIT`；文件超过大小上限 → `BBSV2_UPLOAD_SIZE_LIMIT`（`msg` 带具体上限：图片 10MB / 视频 50MB，

建议 App 上传前本地先校验大小。

响应 `data.attach`（`MRespBbsv2ToolUpload`）：`aid`（后续发帖/回帖传这个）`url`（访问地址；图片是

GIF、没截到封面帧的视频为空字符串）——**图片的 `url` 与图片 / 视频的 `thumb` 都是密文，预览前按 1.10 解密**，

`isimage`（`1`=图片 `0`=视频）`duration`（视频时长毫秒，仅视频有值，图片恒为 `0`）。

### 2.9 CNotify（站内通知，全部需登录）

社区互动通知：点赞（含帖子/评论）、收藏、评论、回复、@提及、关注，共用 `category=1`（社区互动）；
`category=2`（系统消息）包括积分发放通知（`type=credit`）与内容审核结果通知（`type=audit`，见下方
字段说明）。通知为异步生成，
触发后可能有短暂延迟才出现在列表中。同一目标（同一帖子/同一条评论）在未读期间被多人反复点赞/收藏
时会合并成一行、`count` 累加、触发人更新为最新一位，不会刷出多条重复通知；评论/回复/关注/积分
每次都是不同内容，不合并。**自己对自己的互动（给自己的帖子/评论点赞、收藏自己的帖子、回复/评论
自己的帖子、@提及场景里自己回复自己）一律不产生通知**，App 不会收到这类自触发消息。`last_id`/
`category` 不传（或 `category=0`）时 `listCursor` 综合返回全部类型，按 `id desc` 统一排序，不需要
分别拉取各分类再拼接。

#### `GET /bbsv2/notify/listCursor` — 通知列表（游标翻页，游标翻页见 1.5）

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| last_id | int | 否 | 0 | 上一页最后一条的 `id`，不传/0=第一页 |
| per_page | int | 否 | 20 | 每页条数（≤50） |
| category | int | 否 | 0 | `0`=全部 `1`=社区互动 `2`=系统消息，传其它值报 `BBSV2_NOTIFY_CATEGORY_INVALID` |

响应 `data`：`list[]`（`MRespBbsv2NotifyItem`）`next_cursor`（见 1.5）。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 通知 ID |
| type | string | `like`\|`favorite`\|`comment`\|`reply`\|`follow`\|`mention`\|`credit`\|`audit` |
| category | int | `1`=社区互动 `2`=系统消息（`credit`、`audit` 归在这一类下） |
| author | object | 触发者 `uid`（live 用户 ID）/`nickname`/`avatar`/`groupid`/`group_title`；积分/审核通知 `uid=0`、其余字段为空/0 |
| count | int | 合并计数（如"等 23 人赞了你的帖子"），未合并恒为 `1` |
| target | object | 关联目标跳转标识：`tid`/`pid`（0=无）`url`（详情页地址，空=无）；无关联帖子/评论的类型（`follow`/`credit`）全部为空/0；`audit` 见下方说明 |
| info | object | 展示信息：`subject`（所属帖子标题，评论/回复/@提及/审核类通知也带，便于跳转前展示"评论了你的帖子《xxx》"；积分通知=任务名称，如"发帖奖励"；无该文案时为空）`summary`（主题类通知=主题标题，评论/回复/@提及类通知=评论正文摘要，积分通知=积分数量文案，审核通知=审核结果文案，均按访客语言展示，如`"+5 积分"`；**始终有值**——关注类通知落"关注了你"、关联帖子/评论已被删除落"内容已被删除"，App 侧不必对 `summary` 判空） |
| is_read | int | 是否已读 |
| dateline | int | 触发时间戳 |

> `mention`（@提及）不解析正文里的 `@昵称`：回复评论（`post/create` 带 `pid`）时，被回复那条评论
> （`pid`）的作者即为提及目标，与同一次操作触发的 `reply` 通知同时产生（收件人会同时收到 `reply` 与
> `mention` 两条）；直接评论主题（`pid=0`）时不产生 `mention`。
>
> `credit`（积分发放）：Go 积分服务按后台「积分策略」实际发放积分（发帖、新手任务「发帖」「关注」）时写入，
> 本模块只负责展示（2026-10-19 起本模块的发帖、关注接口不再发积分，也不再写这类通知；评论不发积分）。是一条
> `category=2`（系统消息）的通知，`info.subject` 取积分规则名称（如"发帖奖励"）、`info.summary`
> 为本次实发数额的文案（按访客语言展示，如`"+5 积分"`），`target` 恒为空/0。
>
> `audit`（内容审核结果）：后台对待审核的帖子或评论执行「通过 / 驳回 / 删除」时，给作者产生一条
> `category=2` 的通知。`info.subject` 为所属帖子标题（帖子已删除时取审核当时的标题）；`info.summary`
> 为审核结果文案，如"你的帖子已通过审核"、"你的评论未通过审核"，后台填写了原因时拼成
> "你的帖子未通过审核，原因：xxx"（原因为后台填写的原文，不翻译）。`target`：通过、驳回时带
> `tid`/`pid` 与详情页 `url`（作者本人可查看自己未通过的帖子，详情里 `audit_status=3`）；删除时全部
> 为空/0。
>
> 列表与计数只返回上面列出的 `type`。通知表与社区后台（Discuz）共用，后台自身产生的其它通知不会
> 出现在 App 中，也不计入未读数。

### 2.10 CPreload（预加载，公开）

> 专供「App 登录态/游客验签握手还没完成」的场景用，例如分享链接落地页、SSR 页面——此时平台只靠渠道
> （Header `vn-channel` 或同名 param）解析。数据逻辑跟对应的"正常"接口一致，区别是：
> - **免验签**，响应直接带明文 `data`（没有 `sec`，不需要解密，跟直播 `/api/preload/` 同一套规则）；
> - **不接受、也不返回任何依赖登录态的个人化内容**（点赞/收藏/关注状态、草稿、"我的评论"等），未登录
>   也能拿到完整的公开内容；
> - `data` 里额外多一个 `tdk`（页面 Title/Description/Keywords），供落地页/SSR 直接填 `<title>` 与
>   `<meta>`。

共 4 个接口：

| 接口 | 对应正常接口 |
|---|---|
| `GET /bbsv2/preload/threadListCursor` | `thread/listCursor`（2.3） |
| `GET /bbsv2/preload/threadHot` | `thread/hot`（2.3） |
| `GET /bbsv2/preload/threadDetail` | `thread/detail`（2.3） |
| `GET /bbsv2/preload/indexRecommend` | `index/recommend`（2.1），**没有 `tdk`** |

**`tdk` 结构**（前三个接口共用）：

| 字段 | 类型 | 说明 |
|---|---|---|
| title | string | 页面标题 |
| description | string | 页面描述，最长 150 字，超出截断并追加 `…` |
| keywords | string | 页面关键词，西文逗号分隔，去重后最多 8 个 |

`tdk` 只由接口本身查出的数据（帖子标题/版块名/标签/内容类型）与固定站点名 `Falive` 拼装，固定文案按当前请求语言返回（语言口径同
2.3「多语言内容」）；不接后台 SEO 配置。各接口的拼装规则见下方对应小节。

description 里「范围名：标题1、标题2」的冒号与标题分隔符也按请求语言走：简中/繁中/日文为全角 `：` `、`，英文/越南文/泰文为半角
`: ` `, `，波斯文为 `: ` `، `（下文规则表与示例按简中写）。

#### `GET /bbsv2/preload/threadListCursor` — 预加载-帖子列表（公开，游标翻页见 1.5）

逻辑同 `thread/listCursor`，但**没有 `type` 参数**：固定查公开列表，不支持"我的草稿"。

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| last_id | int | 否 | 0 | 上一页最后一条的 `tid`，不传/0=第一页 |
| per_page | int | 否 | 10 | 每页条数（≤50） |
| fid | int | 否 | 0 | 版块 ID，`0` = 平台全部可见版块；不存在/不属于当前平台报 `BBSV2_FORUM_NOT_EXIST` |
| keyword | string | 否 | '' | 标题关键词 |
| digest | int | 否 | 0 | `>0` 仅精华 |
| uid | int | 否 | 0 | 按作者的 live 用户 ID 筛选（作者公开帖子列表），`0`=不筛选；对方还没有社区账号时列表为空 |

（2026-10-20 起；以前取平台名首字母大写，如 `Hc`）。

#### `GET /bbsv2/preload/threadDetail` — 预加载-帖子详情（公开）

逻辑同 `thread/detail`，字段口径一致，区别：

| 项 | thread/detail | preload/threadDetail |
|---|---|---|
| `comment_id` 参数 | 支持 | **不支持**（预加载场景不存在"我的评论"跳转） |
| `is_liked` / `is_favorited` / `favid` | 登录时反映真实状态 | **恒为 `0`** |
| `favorite_count` | 真实值 | 真实值（不分用户，不受登录态影响） |
| `my_comment` | 按 `comment_id` 可能有值 | **恒为 `null`** |
| 浏览数 | 每次调用 +1，返回的 `views` 已含本次 | **不计**，`views` 为库里当前值 |
| `tdk` | 无 | 有 |

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| tid | int | 是 | - | 主题 ID |

不存在/不属于当前平台 → `BBSV2_THREAD_NOT_EXIST`，**`code` 固定为 `-3`**（与 `thread/detail` 同口径）。
**可见范围也与 `thread/detail` 一致**：公开只有已发布且未关闭的帖；带登录态调用时，作者本人额外能看到自己被关闭
（`closed=1`）/ 待审核 / 未通过的帖子（个人化字段仍恒为 `0` / `null`），所以 App 从「我的帖子」点进详情页先调预加载
不会被打回 `-3`；别人访问这些帖仍是 `-3`。
**不计浏览数**：落地页调完预加载后，客户端再调 `thread/detail` 取点赞/收藏状态，浏览数由那一次计，
一次访问只算一次。

`tdk` 规则：

| 字段 | 规则 |

| title | `{帖子标题} \| {站点名}`（分隔符 ` \| ` 跟站内其他页面统一），站点名所有平台都固定为 `Falive` |
| description | 帖子标题 + 帖子标签，视频帖（`mediatype=3`）末尾再加 `视频`（按请求语言），西文逗号分隔，最长 150 字 |
| keywords | 同 description（去重后最多 8 个） |

恒为 `0`；**没有 `tdk`**（首页 TDK 由页面自己定）。

| 参数 | 类型 | 必填 | 默认 | 说明 |
