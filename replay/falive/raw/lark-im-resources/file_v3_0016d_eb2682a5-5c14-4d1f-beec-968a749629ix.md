## P0

### L0 直播流地址一拿到就 403 —— 配置问题，转运维

- 签名里的 `txTime` **刻意取签发时刻**。代码注释写明是防盗流，不改。
- 实际过期时间 = `txTime` + 腾讯云控制台里该播放域名的「鉴权有效时间」。Live 代码和后台都**没有**有效期这个设定。x9 用同一套代码，PRE 实测是 10 分钟。
- 所以「一拿到就 403」不是有效期为 0 的代码问题，而是 `play2zz.sysiyu11.com` 在控制台的配置和后台不一致。可能的原因：
  1. 控制台的鉴权有效时间被设成 0 或极小值；
  2. 后台「平台管理 → 直播配置」里的拉流 key 和控制台的主 KEY / 备 KEY 不一致；
  3. Referer 防盗链白名单里没有新的 web 域名；
  4. 地区或 IP 访问限制。
- 我们会转运维逐项核对。修好后告诉你们实际有效期（预期 10 分钟）。
- 前端这边：
  - `getRoomInfo` 的 `ttl` 参数是**缓存秒数**，不是有效期。保持默认 30 就好，别加大；加大只会让你们拿到更旧的地址。
  - 播放中遇到 403（HLS 刷新 m3u8 过了有效期也会 403），重新调一次 `getRoomInfo` 换地址。你们现在的失败重取逻辑正好适用。
  - SSR 缓存 30 秒 + 前端缓存 3 分钟，在 10 分钟的有效期内没问题。
- `videoType=m3u8` 会强制 `info.pull` 输出 m3u8，并同时填上 `pull_m3u8` 和 `pull_flv`。用法没问题。

### L1 `/api/new_schedule/upcoming` —— 没有，会做〔日期待定〕

- pre 上的 404 是预期内的。这支接口在 10-07「移除纳米 / 火星体育电竞相关代码」时整支删掉了（`new_playlist` 也一样）。之前的 -10501 是服务端 SQL 执行错误，发生在下线前后，不是前端的问题。
- 原接口的语义是「主播预约的足球、篮球、电竞**赛事**」，而且只保留能对上赛事数据的行。falive 没有赛事数据，所以就算留着也永远是空的。
- 我们会按「主播自己建的节目预约」（主播端 `/api/live/setReserveLive` 建的那批：标题、封面、开播时间、简介）重做一支「即将开播」接口。字段见 L13，路径定了再通知。
- 需要和 PM 确认数据源：是用「主播自建预约」，还是后台排的「节目表」。定了才能开工。

### L2 送礼 / 免费礼物 / 余额 —— 部分有

**送礼：有。** `POST /api/member/handSelGift`，需登录。

| 参数 | 说明 |
|---|---|
| `gift_id` | 礼物 id（`Gift/getList` 的 `id`） |
| `anchor_id` | 主播 **uid** |
| `type` | 0 普通礼物（扣钻石，默认）；1 背包礼物（扣背包数量，不扣钻石） |

```json
{"code":0,"msg":"…","data":{"spend":10,"new_balance":990}}
```

- 错误文案：`Parameter error`、`You are mute`、`The recipient must be an anchor`（主播不在本平台也是这条）、`Gift data does not found`、余额不足 `INSUFFICIENT_DIAMOND_BALANCE`。
- 送礼成功后，房间里所有人会收到 WS 消息：
  ```json
  {"method":"notice","action":"gift","vid":"<直播 vid>","gift_id":"12","sender_nickname":"..","sender_exp":"3","sender_exp_icon":"https://..","sender_user_type":2,"seed":"..","platform_id":1}
  ```

**余额：有。** 在 `Member/info` 里：
- `balances`：整数，实时值，和送礼返回的 `new_balance` 口径一致。**用这个。**
- `balance`：格式化字串，满 1 万显示成 `1.2w`。
- 送礼成功后用 `new_balance` 就地更新即可，不用再调一次 info。

**「免费」标记和每日免费额度：没有。**
- 礼物表没有免费栏位，`needcoin ≤ 0` 的礼物会被直接拒收。
- 现有最接近的是**背包礼物**：升级时发放，`/api/gift/getUserGiftList?type=-1` 拿列表（带 `num`），送的时候 `type=1`。但没有「每天 N 个」的规则。
- 一期要的「免费礼物」需要 PM 先定规则：复用背包、每日发放，还是新增「免费 + 每日额度」。定了以后排期〔日期待定〕。在那之前建议礼物面板先只接付费送礼，或者显示「敬请期待」。

### L3 WebSocket —— 有（含契约更正）

**① 契约措辞更正（你们说得对）**
- `wss/?userToken=` 传的是 **API token**：游客 token（`/api/secret/getHot` 下发）或登录 token。
- `getChatToken` 的 `data.token` 是聊天 token，要用 `wss/?token=` 传。
- 两种方式二选一都可以。把聊天 token 放进 `userToken` 会收到 `tokenError` 并断开。答复契约附 B 会照这个更正。
- 补充两点：
  - `heart` 服务端**不回包**，静默忽略，属正常。
  - `sub` / `unsub` 会回 `{"action":"response","code":0,"msg":"SUCCESS-SUB-<vid>"}`。

**② `getChatToken` 的 `mqtt` 和 `version`**
- `mqtt` 是 app 端的备用通道，开关由后端控制，看 `mqtt.enabled`。它不返回 host / port，**web 不用管，只用 WS。**
- `version: "v2.4.1"` 是固定字串，没有对应行为，可以忽略。

**③ 4 类消息体**

所有服务端推送都会带 `method`（`notice` 房间内 / `noticeAll` 全站 / `noticeUser` 单人）和 `platform_id`。

| 消息 | 何时推 | 结构 |
|---|---|---|
| `notice/system` 进房 | **WS 上只推给管理员连接，前台用户收不到**（设计如此）。前台只能在 `chat/history` 第一页看到进房行（`action:"system"`）。要上公屏需改 WS 服务，并评估房间人多时的负载，需 PM 决定 | `{"action":"system","sender":uid,"userid":uid,"vid":"..","msg_type":1,"text":"<昵称> 进入直播间","time":"Y-m-d H:i:s","has_tag":false,"seed":".."}` |
| `notice/inRoom` 进房特效 | 等级 > 9，或 3 天内获得「至尊VIP / 至尊钞神」标签的用户进房时推给房间全员。同一用户同一房间约 16 分钟一次 | 完整聊天消息体（同 `send`）+ `"is_super_vip":bool,"is_super_rich":bool`，`"text":"进入直播间"` |
| `notice/redbag` | 红包活动只发在**聊天群组**（`room_type:1`），直播间本身不会出红包 | 开：`{"action":"redbag","room_type":1,"vid":"<群 vid>","data":{"is_redbag":1,"redbag_text":"..","redbag_time":<倒数结束 ms>,"amount":0,"bar":"0/<上限>","is_ok":0}}`；关：`data:{"is_redbag":0}` |
| `notice/redbagOn` | 有人抢到红包时，推给该群；也推给 `/api/redbag/onRedbag` 的 `notify_vids` 里列出的 vid | `{"action":"redbagOn","room_type":1,"vid":"..","sender_nickname":"..","data":{"status":1,"msg":"恭喜您抢到N金币","amount":N,"total_amount":..,"bar":"x/max","is_ok":0,"is_repeat":0}}` |
| `noticeAll/toggle` 切播 | 主播开播、连播（改直播资料）时推送 | `{"method":"noticeAll","action":"toggle","userid":<主播 uid>,"vid":"<vid>","data":{"match_id":0,"channel":"toggle","user_id":<主播 uid>}}`。注意顶层键名是 `userid`。会推给**全站所有连接**，前端要按 vid / uid 过滤 |

顺带两个相关的全站推送：
- 下播：`{"method":"noticeAll","action":"closeLive","vid":"..","userid":uid}`
- 开播通知粉丝：`{"method":"noticeUser","action":"startLive","userid":uid}`

**④ `liveHeat`（补文档）**

```json
{"method":"noticeAll","action":"liveHeat","live_room_online_counts":{"<vid>":123,"<vid2>":45}}
```

- 大约每 2 秒推一次，推给全站。数值每 30 秒重算一次。
- 只列出正在直播的房间。
- 值是「直播间在线人数（含灌水）」，和 `getRoomInfo` 的 `userData.live_room_online_count` 是同一个数（见 L15），可以拿来实时刷新观看人数。

### L4b 邮箱 + 验证码登录 —— 支持

```
POST /api/user/NewMailLogin
mail        = RSA 密文（同密码登录）
code        = 明文数字（sendVerificationCode 发的登录验证码：mail + type=3）
device_type = web
```

- 有 `code` 时走验证码登录，不需要 `password`。
- 只有当 `code` 被解析成 0 时，才会落到密码登录，返回「请输入您的密码!」。可能的原因：栏位名不对、值为空、或传了非数字（比如把 code 也做了 RSA 加密）。
- 请把实际请求体（去掉密文）贴给我们，我们帮你们对。
- 另外，后台「注册方式」没开邮箱时，会返回「The current login method has been closed」。

## P1

### L5「我的预约」—— 有接口，但要改〔日期待定〕

- 现有接口：`GET /api/live_streaming/getUserReserveLiveList`，需登录。
  - **缺**节目标题、开播时间、封面，而且行里的赛事栏位都是空字串。
  - 预约按「赛事 id」记，非赛事节目都是 0。同一分类连续预约两个节目时，第二次会把第一次**取消掉**。
- 预约 / 取消：`POST /api/live/reserveMatch?live_id=<节目 id>`，是 toggle。
- 我们会把预约改成按节目 id 记录，列表补上：节目 id、标题、封面、开播时间、是否在直播、主播 uid / 昵称 / 头像。和 L1 一起做。

### L6 / L7 推荐视频、录播列表与详情 —— 没有，需 PM 决定

- `new_playlist/allLiveList` 不是录播。它原本是「主播可开播的赛事清单」，也随体育代码下线了。
- 录播数据本身是有的（腾讯云点播：m3u8、封面、时长），但目前只有一支给嗨聊用的「按主播取录播」接口，不适合 web 用。
- 缺的部分：跨主播的推荐列表、单个视频详情、相关推荐。另外**没有观看数**这个数据。
- 需要 PM 确认一期要不要。要的话我们排期〔日期待定〕；不要的话，前端先下掉或显示「敬请期待」。

### L8 直播间留言板 —— 没有

- 目前只有新闻（头条）评论，没有直播间留言板。
- 需 PM 决定做不做。暂时维持「敬请期待」。

### L9 直播间预告 —— 有

`GET /api/LiStre/getReserveLiveList?uid=<主播 uid>`，游客可用。返回这位主播之后的预约：最多 20 条，按开播时间升序。

```json
{"code":0,"data":[{"id":12,"uid":10086,"title":"周五晚盘前分析","thumb":"/upload/..","starttime":1760000000,"bulletin":"..","reserve_num":3,"is_reserve":0}]}
```

- 主播不属于当前平台时，返回空数组。
- `thumb` 目前返回的是不带域名的相对路径，我们会改成带域名的完整地址〔日期待定〕。在那之前，前端拼上图片域名即可。
- `is_reserve` 有和 L5 相同的问题，随 L5 一起修。
- 别用 `/api/live_streaming/getReserveLiveList`（同名）：游客调永远是空的。

### L10 直播间聊天历史 —— 有

`GET /api/chat/history?vid=<直播 vid>&room_type=0&last_id=0&limit=20`

- 由新到旧返回。往前翻时，`last_id` 传已拿到的最小 `msg_id`。
- 每条的结构和 WS `send` 消息体相同：`msg_id, seed, vid, sender, sender_nickname, sender_exp, sender_exp_icon, avatar, text, msg_type, pic, time, time_ms, room_type, color, designation ...`。
- 第一页在服务端缓存 5 秒。聊天少于 `limit` 条时，会补进房行（`action:"system"`）。
- 别用 `chat/getChatHistory`：它会顺带标已读。

### L11 私聊、群组 —— 有

身份都从 token 取。

| 用途 | 路径 | 参数 |
|---|---|---|
| 会话列表（群组 `room_type=1` + 私聊 `room_type=2`） | `chat/getChatRoomList` | — |
| 历史 | `chat/history` | `vid, room_type, last_id, limit` |
| 发言（已有 vid） | `chat/sendMessage` | `vid, type`（= room_type）, `msg_type`（1 文字 / 2 图片）, `text` |
| 标已读 | `chat/read` | `vid` |
| 找主播私聊（不用 vid，自动分配助理） | `chat/sendToAnchor` | `anchorId, text, msgType, pic, seed` |
| 主播私聊历史 | `chat/anchorHistory` | `anchorId, last_id, limit` |
| 找助理私聊 | `chat/sendToAssistant` | `assignId, text, msgType, pic, seed` |

- 群组由后台建、后台拉人。用户只看得到自己所在的群，不在群里调历史会返回 `Chat Group does not exist`。

### L12 直播间签到 —— 有，属于任务中心

- 签到不是直播间独立功能，是任务中心的「签到」任务：
  - 签到：`/api/task/update?code=checkin`。第一次调是签到，再调一次是领奖。
  - 补签：同一接口带 `date=YYYY-MM-DD`，限注册用户、当月、每月 3 次。
  - 状态：`/api/task/show/code/checkin`。任务列表：`/api/task/list`。
- 直播间按钮可以直接调上面的接口，或者跳任务中心。

## P3 口径确认

**L19 错误码**

web 端的业务错误码一律是负数，通用错误是 `-1`。

| 码 | 意思 | 前端处理 |
|---|---|---|
| `-1` | 通用业务错误，看 `msg`（已翻译） | 显示 msg |
| `-666` | 请求太频繁（HTTP 429），见 L27 | 稍后重试 |
| `-700` | 未登录或登录失效 / 缺 token | 重新登录，或重取游客 token |
| `-800` | 验签失败（HTTP 401/407） | 检查签名 |
| `-888` | 客户端时间与服务器相差超过约 ±60 秒（HTTP 402） | **SSR 服务器要开 NTP 校时** |
| `-10501` | 不是业务码，是服务端 SQL 执行错误 | 请回报给我们 |

- 没有专门表示「不存在」的码：数据不存在是 `-1` + `Data does not exist`。接口路径不存在是 HTTP 404。

**L20 房间不存在**

- 主播不存在，或不属于当前平台：HTTP 200，`code=-1`，`msg=Data does not exist`。前端可以按这个回 404 页。
- 主播存在但没开播：这是**成功返回**，`info.islive≠1`、`pull` 为空。这不该是 404。
- 有一个边角情况：uid 存在但不是主播时，可能会走到 500。我们会修成同样返回 `-1`〔日期待定〕。

**L27 限流阈值**

- 计数按「每台后端节点、每个接口、每 1 秒」算，默认基准 N = 4（发言 6）：

  | 维度 | 超过 | 结果 |
  |---|---|---|
  | 同一设备（OaID） | 8 次/秒 | 429 / `-666` |
  | 同一访客 | 4 次/秒 | 429 / `-666` |
  | 同一 IP | 28 次/秒 | IP 级拦截。公网 IP 且带访客标头时，该 IP 所有接口被拒 10 秒 |
  | 同一个签名 5 秒内重复 | 12 次 | 451，会被高防封 300 秒 |

- `/api/preload/*` 一样受限流管。
- SSR 回源如果不带 OaID，所有用户会挤在同一个计数桶里，很快就会 429。目前**没有**限流白名单。
- 两种做法，请你们选：
  1. 我们加一个「SSR 出口 IP 免限流」的配置〔日期待定〕，然后你们提供 pre / uat / online 的 SSR 出口 IP；
  2. SSR 透传每个用户的 OaID / 访客标头，再加上你们自己的缓存。
- 建议 1 + SSR 缓存一起做。

**L25 排行榜**

- 话痨榜 `GET /api/ranking/speaking?type=daily|weekly`
  - 统计周期：`daily` 是当天，`weekly` 是本周一到周日（服务器时区）。
  - 只算本平台**注册用户**在**直播间**的发言条数。
  - 每小时整点算一次前 10 名。
  - 字段：`user_id, count, user_nickname, avatar`。之前文档写的 `speak_count` / `nickname` 是错的，以这个为准。`limit` 最多有效 10。
- 贡献榜 `GET /api/leaderboard/user?type=0|1|2`
  - 统计周期：0 本周，1 本月，2 总榜。
  - `amount` = 送出礼物的钻石数 × 后台「人气倍数」，是格式化字串（如 `1.2w`）。
  - `msg` 是距离本期结束的倒计时文案。
  - 主播榜 `/api/leaderboard/anchor` 周期相同。直播间内的贡献榜：`/api/live_streaming/roomRanking?uid=&type=0`（今日）/ `1`（本周）。
