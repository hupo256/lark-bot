# 修改头像接口（前端接入）

更新日期：2026-10-23。适用：Live、HiChat 客户端接入 Go 统一头像功能。

## 1. 接入结论

**选择图片 → 一次上传到 Go → 图片安全校验 → 直接修改并同步 Live、HiChat、Discuz。无人工审核，无需第二次修改调用。**

| 方法 | Go 服务内路径 | 用途 |
|---|---|---|
| POST | `/api/auth/avatar/upload` | 上传图片并修改头像，唯一修改入口 |
| GET | `/api/auth/avatar/requests/{request_id}` | 查询本人某次修改的处理状态；通常用于超时、失败或刷新待完成时 |

原 `PUT /api/auth/avatar` 已删除，不再接收头像 URL 修改请求。`PUT /api/auth/profile` 仍用于其他资料，但不能传非空 `avatar`，否则返回参数错误。

不要再调用 PHP、Java 的头像上传、头像修改或待审核头像查询接口，也不要等待管理员审核通过。这里的图片安全校验是文件格式、解码与资源限制校验，不是图片内容审核。

## 2. 基础约定

- 请求发送到 Go 域名。下文 `BASE_URL` 为环境提供的 Go 访问基地址，不包含结尾 `/`。
- 使用外层网关 `/go-api` 时，`BASE_URL` 示例为 `https://api.example.com/go-api`；完整上传地址为 `https://api.example.com/go-api/api/auth/avatar/upload`。直连 Go 则不加 `/go-api`，以部署提供的地址为准，不重复拼接前缀。
- 两个接口都要求 `Authorization: hiApp <token>`。`token` 必须取 Go 登录响应里的 portal `token`，不是 `live_token`、`hichat_token`，也不能直接使用 PHP/Java 原登录凭证。
- 游客不可用。Live、HiChat、Discuz 账号映射须完整，由服务端根据登录用户判断；前端不传用户 ID。
- 修改头像不会使现有登录凭证失效，不要求重新登录。只有遇到 `code=-700` 才按登录失效处理。
- 可带 `X-Request-ID` 用于排查。它不能代替表单中的业务幂等字段 `request_id`。

## 3. 上传并修改头像

```http
POST /api/auth/avatar/upload
Authorization: hiApp <Go portal token>
Content-Type: multipart/form-data; boundary=<客户端自动生成>
```

### 3.1 请求参数

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `request_id` | string | 是 | 8–64 位 ASCII 字母、数字、下划线或连字符，建议 UUID；同一次操作重试必须不变 |
| `file` | 文件二进制 | 是 | 一张图片，限制见下节 |

只接受这两个字段各一次。不要传 `avatar`、`user_id`、`platform_code` 等额外表单字段，不带 URL 查询参数。不要发送 JSON、base64、多个文件或 gzip 等压缩请求体。

使用浏览器 `FormData`、App 原生 multipart 或 curl 的 `-F` 时，由客户端生成 Content-Type 和 boundary；不要沿用通用 JSON 请求封装的 Content-Type。

### 3.2 图片要求

| 项目 | 要求 |
|---|---|
| 文件大小 | 不超过 5 MiB，即 5,242,880 字节 |
| 文件格式 | JPEG/JPG、PNG、GIF；以实际可解码内容为准，不只看扩展名或 MIME |
| 图片宽、高 | 每一边不超过 4096 像素 |
| 总像素数 | 宽 × 高不超过 8,000,000；例如 4096 × 4096 不允许 |
| 不支持 | WebP、HEIC、SVG、HTML、非图片及损坏文件等 |
| 服务端处理 | 重新编码去除 EXIF/附加数据；JPEG 输出 JPEG，PNG 输出 PNG，GIF 仅取第一帧并输出 PNG |

前端在上传前完成裁剪和方向旋正；需要转换 HEIC/WebP 等格式时也在上传前完成。**生成本次上传任务后保留最终文件字节与 request_id，重试时不能重新压缩、裁剪或转换格式。**

响应只返回最终主图 URL，不返回单独的缩略图字段。优先直接使用 `data.avatar`，不要沿用本地文件名、输入扩展名或旧头像 URL。

### 3.3 请求示例

```bash
curl -X POST "${BASE_URL}/api/auth/avatar/upload" \
  -H "Authorization: hiApp ${TOKEN}" \
  -F "request_id=0fb933ea-61e2-4aae-b97d-f090ec456d5e" \
  -F "file=@/path/to/avatar.png"
```

浏览器请求示例（不包含 UI 和自动重试逻辑）：

```javascript
async function uploadAvatar(baseURL, token, requestId, file) {
  const form = new FormData();
  form.append("request_id", requestId);
  form.append("file", file);
  const response = await fetch(`${baseURL}/api/auth/avatar/upload`, {
    method: "POST",
    headers: { Authorization: `hiApp ${token}` },
    body: form,
  });
  const result = await response.json();
  return { httpStatus: response.status, result };
}

async function getAvatarChange(baseURL, token, requestId) {
  const response = await fetch(
    `${baseURL}/api/auth/avatar/requests/${encodeURIComponent(requestId)}`,
    { headers: { Authorization: `hiApp ${token}` } },
  );
  const result = await response.json();
  return { httpStatus: response.status, result };
}
```

调用方在用户确认图片时生成一次 UUID，并与该文件一起保留；重试把原值传给 `uploadAvatar`，不要在函数内部每次生成新 ID。调用方还须捕获网络错误、取消请求、网关非 JSON 响应等异常，并按第 5 节查询原请求。

### 3.4 成功响应

HTTP 200：

```json
{
  "code": 0,
  "msg": "Operation successful",
  "data": {
    "request_id": "0fb933ea-61e2-4aae-b97d-f090ec456d5e",
    "avatar": "https://cdn.example.com/avatar/u20001/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa/avatar.png",
    "status": "COMPLETED",
    "version": 1792710000123
  }
}
```

| 字段 | JSON 类型 | 说明 |
|---|---|---|
| `code` | number | `0` 成功；`-700` 登录失效；`-1` 参数、业务或服务错误 |
| `msg` | string | 提示文案，不把英文成功文案作为成功判断条件 |
| `data.request_id` | string | 本次操作 ID，与请求一致 |
| `data.avatar` | string | 最终头像的完整公开 URL，前端用它更新本地展示 |
| `data.status` | string | `COMPLETED` 或 `REFRESH_PENDING`；上传成功响应不会是 `PENDING` |
| `data.version` | number | 服务端生成的单调毫秒版本，不是前端传入时间，不按字符串收发 |
| `data.retry_count` | number | 当前处理阶段累计失败次数；为 0 时省略，前端缺省按 0 处理，不是前端必须重试的次数 |
| `sec` | string | 未启用 API AES 时省略；启用后为 data 的加密副本，明文 data 仍可直接使用 |

**上传返回 `code=0` 时，三端数据库头像均已修改。** 立即用 `data.avatar` 更新本人头像和前端本地用户资料缓存；不需要再次调用修改接口，也没有 `uploadSuccess` 或待审核状态。

`REFRESH_PENDING` 仍是修改成功，表示缓存/IM 刷新投递需要后台重试；其他端显示可能稍晚更新。`COMPLETED` 也不表示每个离线设备已经收到或处理消息。

## 4. 查询修改状态

```http
GET /api/auth/avatar/requests/0fb933ea-61e2-4aae-b97d-f090ec456d5e
Authorization: hiApp <Go portal token>
```

路径参数 `request_id` 与上传时完全一致；不带请求体，只能查询当前登录用户自己的请求。成功外壳和 data 字段与上传相同。

| `data.status` | 含义 | 前端处理 |
|---|---|---|
| `PENDING` | 目标已保存，三端数据库尚未全部完成，可能部分成功 | 显示“正在同步”，继续有限次数查询，必要时原 ID + 原文件重试上传；不要提示已全部失败或已回滚 |
| `REFRESH_PENDING` | 三端数据库完成，缓存/IM 刷新待重试 | 使用新头像，不要求用户重新上传；可以稍后查询 |
| `COMPLETED` | 数据库完成，刷新处理及消息投递完成 | 使用新头像，停止本次状态查询 |

查询 `code=0` 只代表查到了记录，必须再看 status；不能把查询返回的 `PENDING` 当作修改完成。GET 只读，不会主动触发重试。

查不到记录时返回 HTTP 200、`code=-1`、`msg="头像修改记录不存在"`，不是 HTTP 404。目标可能尚未持久化，也可能原请求还在处理；保持原 ID 和文件，不直接换新 ID。

查询返回的是**这次请求的历史目标**，不保证它是用户现在的头像。若用户已经发起了更新的头像操作，迟到的旧响应不得覆盖最新 UI。只处理当前活动 `request_id`，页面刷新后获取当前资料可使用 `GET /api/auth/profile`。

## 5. 异常与重试

| 场景 | HTTP | code | 前端处理 |
|---|---|---|---|
| 未登录、过期凭证、游客 | 200 | -700 | 走登录流程，不能只根据 HTTP 200 当作成功 |
| 字段缺失、非法 ID、文件无效/超限、错误 multipart | 400 | -1 | 提示参数错误；修正文件后作为新操作生成新 ID，不反复发送坏请求 |
| 同 ID 对应不同图片、上一请求未完成、账号映射不完整、记录不存在 | 200 | -1 | 展示 msg；区分查询原请求、等待同步和重新登录/联系支持，不盲目循环重传 |
| 数据库同步中途失败 | 200 | -1 | 查询原 request_id；后端可能已保存任务并在重试，不认定全部回滚 |
| 上传存储未配置/不可用、三端功能未开启、并发已满 | 503 | -1 | 有限退避后重试，仍使用原 ID 和文件；持续失败联系后端 |
| 网络断开、客户端超时、网关 5xx | 不固定 | 可能无标准外壳 | 结果未知，优先查询原请求，不生成第二次修改 |

业务失败示例：

```json
{
  "code": -1,
  "msg": "三端资料同步失败，请稍后重试",
  "data": []
}
```

错误时 data 可能是空数组，不能按成功对象读取。不要依赖一定存在 reason；服务端 5xx 的 msg 会隐藏内部详情。Go 业务接口不会用 HTTP 401 表示登录失效。

建议的前端流程：

1. 用户确认新图片：生成一个 request_id，保存最终上传文件，禁用重复提交按钮，发一次 POST。
2. POST `code=0`：更新本地头像。COMPLETED 结束；REFRESH_PENDING 也是成功，按需稍后查询。
3. 网络异常或数据库失败：使用原 ID 查询。PENDING 等待；REFRESH_PENDING/COMPLETED 使用新头像；记录不存在且属于瞬态故障时重试原 POST。
4. 查询或重传可采用 1、2、4、8 秒等有限退避，例如约 1 分钟后停止自动等待并保留待处理状态供用户稍后查询。不要创建无限轮询，不要一次并发多次上传。
5. 原任务数据库未完成前，不用新 ID 强行覆盖。后端自动同步也有重试上限，长期未完成交由后端排障；不是前端重新登录就一定能解决。

## 6. 联调验收清单

- 正常上传只发一次 POST，返回新 URL；Live、HiChat、Discuz 头像随后一致，无人工审核页面。
- 旧 `PUT /api/auth/avatar` 不再调用，资料更新请求不携带 avatar。
- 相同 request_id + 相同文件重复提交不重复修改；相同 ID + 不同文件被拒绝。
- 超时后可以查询原请求；数据库故障时不把部分完成误报为已回滚。
- REFRESH_PENDING 按修改成功展示；旧请求的迟到响应不覆盖新头像。
- 上传支持 JPEG/PNG/GIF，超限或损坏文件被拒绝；GIF 显示为静态第一帧。
- 返回的 URL 在各客户端网络中可访问，跨端缓存/聊天头像刷新符合预期。
- 上传后原登录态仍然可用；无效 Go token 返回 code=-700。

本文件可单独交给前端，不要求阅读后端实现说明。multipart 上传使用手工路由，自动生成的 OpenAPI 不包含其上传格式，接入以本文件为准。
